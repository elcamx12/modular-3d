# 통합 총평

## 한 줄 결론
**"엔진은 대학원 수준, 차체·조립라인·계기판은 졸업작품 수준."** 계산 코어(구조해석·하중·단면설계·운송 패킹·캐시·직렬화)는 도메인 이해가 깊고 정직하게 잘 짜여, 코드감사에서 시비의 약 절반이 정직하게 기각됐다. 반면 *보여주기(렌더)·이어주기(탭 데이터흐름)·반복시키기(워크플로우)·꾸미기(UI)* 는 한 줄기로 안 묶였고, *모듈러 도메인의 정수(건식접합 거동·인양/운송 구조·층간변위)* 는 가장 얕게 다뤄진다. 치명(크래시·잘못된 안전판정) 결함은 0건 — 가장 우려한 해석 수렴실패도 예외로 표면화된다.

# Part I — 심층 제품·도메인·렌더·UX·아키텍처 피드백 (L1~L6)

> 방식: 코드만 보고(스크린샷 없음), 구조·운송 스터디 범위 내에서 공정하게.
> 각 발견: 제목 → 코드 근거(파일:라인) → 영향 → 리팩토링 방향 → 심각도(구조적/큼/중간/작음).

## L1. 렌더링·기하 정합

### L1-1. 3D 뷰가 "설계한 단면"을 안 보여준다 (WYSIWYG 붕괴) — 구조적
- 근거: model/core.py:63-83(BeamData/ColumnData section_w/h 기본 200 고정), 201-209(_apply_beam_section_type 가 section_type[shs/h]만 전파, 치수 미변경), render/mesh_builder.py:335/349-366(이 section_w/h 로 메시 생성). 전 코드에 설계 단면치수를 BeamData.section_w/h 로 write-back 하는 곳 없음(grep 확인).
- 문제: 단면설계가 보를 H400, 기둥을 250각으로 수렴시켜도 형상은 항상 200×200. 3D 화면은 설계 결과와 무관한 균일 막대.
- 영향: 설계 도구인데 "내가 키운 부재가 화면에서 안 굵어짐". 구조 검토 결과를 시각으로 못 읽음. 역설적으로 이래서 "사이즈 다를 때 겹침"이 화면엔 안 나타남 — 문제를 푼 게 아니라 사이즈를 무시해 덮은 것.
- 리팩토링 방향: 단면설계 수렴 후 design_section 의 실치수를 각 BeamData/ColumnData 로 1회 write-back(렌더 전용 갱신 패스). 또는 mesh_builder 가 design_result 를 직접 참조해 그리기. 단, 키운 단면이 인셋(200 가정)을 넘으면 L1-2 의 겹침이 드러나므로 인셋도 단면폭 연동 필요.
- 연결: 감사 E009·M006.

### L1-2. 인셋·갭이 컴포넌트 크기와 무관하게 200 고정 → 크기 다른 이웃끼리 면 어긋남 — 큼
- 근거: model/core.py 전 generate_sub_components 가 s=_SECTION_W(200) 고정 인셋(보 start=s..w-s, 슬래브 4변 s). 모듈-모듈 갭은 카탈로그 MODULE_JOINT_GAP_MM=20 고정.
- 문제: 폭·깊이 같은 모듈끼리는 보 윗면+슬래브가 연속돼 깔끔하나, 깊이가 다른 모듈을 나란히 두면 양쪽 가장자리 보가 다른 위치 → 바닥 가장자리가 계단처럼 어긋남. 비내력 벽채움(두께 100)을 인접 모듈마다 각자 그려 공유 면에 이중벽(100+20+100), 폭 다르면 벽 끝 빈틈.
- 영향: 표준치수만 쓰면 안 드러나나 임의 치수 허용이라 잠복. 혼합 치수 배치 시 시각 품질 저하·실제 접합 의문.
- 리팩토링 방향: 인접성 인지 슬래브/벽 생성(공유 면에서는 한쪽만 벽, 면 맞춤). 또는 모듈 치수를 표준 그리드로 제약하고 비표준은 경고. 최소한 인셋을 실제 단면폭과 연동.

(2) render/viewer_three_template.html(540줄, three.js 정의/배치뷰). (3) ui/alignment/alignment_view_three_template.html(914줄, three.js 정렬뷰). (4) transport/loaded_3d_three.py:442~ 인라인 _HTML_TEMPLATE(three.js 운송/물량뷰) + _serialize_body_parts/_serialize_wall_segment/_serialize_attached_part.

### L2-2. three.js 씬을 3곳에서 각각 CDN 재로딩·재부팅 + 오프라인 취약 — 큼
- 근거: 3개 three.js 표면(viewer_three_template, alignment_view_three_template, loaded_3d_three 인라인)이 각자 three.min.js(r128)·OrbitControls·CSS2DRenderer 를 cdnjs/jsdelivr CDN 에서 로드(loaded_3d_three.py:522-524)하고 scene/camera/light/raycaster/OrbitControls/qwebchannel 를 독립 구성(622~).
- 문제: (1) 씬 부트스트랩·피킹·카메라 보일러플레이트가 3중복(540+914+인라인). (2) three.js 를 외부 CDN 에 의존 → 데스크톱 앱이 오프라인이면 모든 three.js 뷰(정의·정렬·운송)가 깨짐. 부트스트랩이 한글경로·WebEngine 까지 공들였는데 정작 핵심 JS 가 네트워크 의존.
- 영향: 오프라인 작업 불가(설계 현장·폐쇄망서 치명적일 수 있음). 씬 설정 바꾸면 3곳 손봄.
- 리팩토링 방향: three.js·컨트롤을 로컬 동봉(vendor)하고, 공통 three 셋업/피킹/카메라를 단일 JS 모듈로 추출해 3뷰가 공유. 템플릿은 컨테이너+데이터만.

### L2-3. 운송 직렬화를 "회귀 차단"용으로 의도적 복제 — 중간
- 근거: transport/loaded_3d_three.py:1412 주석("운송 serialize_pack_for_three 와 *분리*(운송 회귀 차단)"), serialize_quantity_for_three(1462) 가 serialize_pack_for_three(335) 를 거의 복제 + hide_truck 등 소소한 차이.
- 문제: 추상화(공통화) 대신 복붙으로 회귀를 격리하는 전형. 당장은 안전하나, 부재 직렬화 규칙이 바뀌면 pack/quantity 두 벌을 따로 고쳐야 하고 시간이 지나며 어긋남.
- 영향: 운송 3D 와 물량 3D 가 같은 부재를 미세히 다르게 그릴 수 있음. 유지보수 2배.
- 리팩토링 방향: 공통 _serialize_item 코어 1개 + (트럭표시/숨김 등) 옵션 파라미터화. 회귀는 복붙이 아니라 테스트로 차단.

## L3. 탭 간 데이터 흐름

### L3-1. 단일 "프로젝트 결과" 없이 탭마다 재빌드 + 임시 넘겨주기 — 구조적
- 근거: ui/main_3d_joint.py:82-83(접합 뷰가 build_analysis_model+build_ops_model 자체 호출), ui/main_3d.py:1642-1644(단면설계용 am 또 빌드), analysis_panel solve 도 빌드. 설계결과는 controller._design_results 사적 속성(main_3d.py:1364 getattr), 운송탭엔 populate_transport→set_design_result 로 밀어넣음. 1223/1364/1651 의 hasattr/getattr 방어 패턴 = 느슨한 임시 연결.
- 문제: 같은 토폴로지(AnalysisModel)를 탭마다 독립 재계산. 결과가 한 객체로 안 모이고 "속성 있으면 꺼내 쓰고 / 다음 탭엔 push" 식. 단일 진실원천(프로젝트 파이프라인 상태) 부재.
- 영향: (1) 재계산 낭비 (2) 한 탭 변경이 다른 탭에 stale (3) hasattr 가드 누락 시 조용한 미반영 (4) 신규 탭 추가 시 push 배선 수작업.
- 리팩토링 방향: scene→AnalysisModel→DesignResult→Quantity/Transport 를 단계 캐시(운송의 TransportCache 처럼)로 묶은 ProjectModel/파이프라인 객체 1개. 탭은 그걸 구독(읽기)만. 운송탭이 이미 8단계 캐시를 가진 좋은 선례 — 그 패턴을 전 파이프라인으로 승격.
- 연결: 감사 T003·T004·H004·O001.

### L3-2. 캐시·무효화가 운송에만 있고 해석 파이프라인엔 없다 — 중간
- 근거: transport/cache.py 의 8단계 fingerprint·invalidate_from 은 운송 한정. 해석→단면설계→물량 경로엔 동등한 단계 캐시·무효화 규약 부재(각 탭이 build_analysis_model 등을 직접 호출, L3-1).
- 문제: 운송은 "입력 안 바뀌면 재계산 안 함 + 바뀌면 자동 무효화"가 잘 되는데, 정작 더 무거운 해석·단면설계는 그 보호가 없어 탭 들어갈 때마다 재빌드하거나, 반대로 모델이 바뀌어도 한 탭이 옛 결과를 들고 있을 위험(stale)이 양립. 좋은 패턴이 한 모듈에 갇혀 있음.

- 리팩토링 방향: TransportCache 의 fingerprint/invalidate_from 설계를 해석·단면·물량까지 일반화한 공용 파이프라인 캐시. L3-1 의 ProjectModel 과 한 몸으로.

### L4-1. 횡변위는 구하면서 "층간변위비(drift)" 한계 검토가 없다 — 큼·구조적

- 영향: 횡력에 유연한 모듈러 건물의 사용성·안전 핵심 지표를 사용자가 직접 눈대중. 합격/불합격 판정 부재.
- 리팩토링 방향: lateral 결과에서 인접 층 마스터노드 변위차/층고 → 층간변위비, 케이스별 max 와 허용한계 비교를 strength/evaluation 에 추가. 이미 횡변위는 있으니 한 스텝.

### L4-2. 운송 모듈인데 "인양·운송 중 구조검토"가 전무 — 큼
- 근거: 전 코드에 인양/lifting/양중/크레인/운송하중/가속도/erection 매칭 0건(grep). transport 는 트럭 적재(packing)·비용·회차만. 구조해석(ops)은 in-service 중력+지진+풍만.
- 문제: 모듈러에서 가장 위험한 구조 케이스는 흔히 **인양(4점 지지 시 모듈 자중 모멘트·러그 반력)과 운송(도로 가·감속·횡가속도, 노면 충격)** 인데, 도구가 모듈을 트럭에 "싣는 물류"만 다루고 그 하중상태에서 모듈이 버티는지는 안 봄. in-service 로 설계된 단면이 인양/운송서 깨질 수 있음.
- 영향: 운송탭이 "운송 가능/비용"은 답하지만 "운송해도 모듈이 안 망가지나"는 답 못 함. 모듈러의 핵심 리스크 사각.
- 리팩토링 방향: 운송 입력(모듈 치수·자중·단면)으로 인양 케이스(4점/2점 지지 단순보)·운송 관성하중(0.5g 횡·1g 상하 등) 약식 검토를 운송탭에 한 칸 추가. 이미 단면·자중 데이터가 운송 adapter 에 다 있음 — 재활용 가능.
