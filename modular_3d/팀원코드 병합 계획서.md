## 0. 상황 요약 (왜 이 방식인가)

- 우리 저장소 루트는 `my_project`, 팀원 폴더는 자체 `.git` 을 가진 별도 클론이다.
- **두 작업본 모두 같은 공통 베이스 커밋 `97a3ccc` 위에 올라가 있고, 양쪽 다 커밋·푸시하지 않은 작업 폴더(working tree) 변경만 쌓아둔 상태**다. 즉 깃허브(origin/main)에는 둘 다 안 올라가 있으며, "누가 최신이냐"가 아니라 **공통 베이스 대비 각자 무엇을 바꿨는가**를 비교하는 것이 정확한 방법이다. (깃허브 푸시 여부와 무관하게 로컬에서 완전 비교 가능)
- **작업 영역이 거의 분리되어 있다.**
  - 우리: 단면 설계 탭 신설, 운송 패킹, 렌더링 (변경량 큼)
  - 팀원: 평가('종합'으로 개명) 탭 개편, 공정표, **비교 탭 신설** (변경량 큼)
- 이 분리 덕분에 진짜 같은 줄을 다르게 고친 충돌은 거의 없고, 대부분 "같은 파일의 다른 부분" 또는 "한쪽만 대규모, 한쪽은 소규모"다.

### 의사결정 기록 (사용자 확정)
- ✅ 병합 방향: **우리 코드 기준 흡수**
- ✅ 평가 탭 이름: **'평가' → '종합' 으로 개명** (팀원 변경을 따른다, 비교 탭 추가와 한 세트)
- ✅ 이 계획서의 청사진대로 진행
- ✅ 이번 단계는 분석·계획 확정까지. 실제 파일 병합은 본 계획서 기준으로 후속 수행.

## 3. main_3d.py 병합 항목 (가장 중요)

우리 버전을 베이스로 두고 팀원 추가분을 얹는다. 구체 항목:

### 3-1. 탭 인덱스 재배치
- 현재 우리: 0정의 1배치 2접합 3구조해석 **4단면설계** 5물량 6운송 7공정표 8평가
- 병합 후: …8**종합** **9비교**
- 작업: 탭 상수에 `TAB_COMPARE = 9` 추가(팀원은 8로 만들었으므로 +1 조정). `TAB_EVALUATION = 8` 유지.

### 3-2. 비교 탭 생성·연결
- `from .compare_panel import ComparePanel` + `self._tab_compare = ComparePanel()` 생성
- `addTab(self._tab_compare, '비교')` 를 평가(종합) 탭 다음에 추가
- `_on_tab_changed` 에 `elif idx == TAB_COMPARE:` 분기 추가 — 공유 위젯 정리(치수 패널 deactivate/숨김, 변형형상 숨김), 자동주입 없음(비교탭은 자기 `.case.json` 로드만 사용)

### 3-3. 평가 탭 → '종합' 개명
- `addTab(self._tab_evaluation, '평가')` 의 라벨을 `'종합'` 으로 변경. (상수명 `TAB_EVALUATION` 은 유지 — 코드 영향 없음)

### 3-4. 평가 데이터 저장 버그 수정 = **필수 반영**
- **현상**: 우리 코드의 평가 저장 경로(`_on_evaluation_save_case`)는 `build_evaluation_data(... design_results=, transport_result=)` 옛 인자로 호출한다. 그러나 함수의 정상 시그니처는 **베이스부터 새것**(`quantity_reports`/`current_policy`/`transport_pack`/`transport_eco`)이라, 옛 인자엔 해당 키가 없어 **저장 버튼을 누르면 `TypeError` 로 죽는다.** (베이스부터 박힌 버그)
- **팀원이 정확히 이 부분을 고쳤다.** → 팀원의 수정(인자를 `quantity_reports`/`current_policy`/`transport_pack`/`transport_eco` 로 교체, 값은 `_analysis_panel._quantity_reports`·`_current_policy`·`_last_transport_pack`·`_transport_tab._last_eco` 에서 수집)을 그대로 가져온다.
- 우리 탭 진입 경로(`_on_tab_changed` 의 평가 블록)는 이미 새 시그니처로 정상 — 손대지 않는다.

### 3-5. 평면도 캡처 (비교/종합탭 표시용)
- `_capture_layout_full_pixmap` 메서드 신설 — 배치설계 2D 캔버스를 현재 zoom/pan 과 무관하게 fit-all 로 캡처 후 상태 원복. 캡처 시 `compare_panel._CaseSlot._whiten_dark_pixels` 로 검은 배경 흰색화.
- 종합탭 진입 시 `set_layout_pixmap(pm)` 호출, 저장 시 PNG bytes 를 `save_case(... layout_png_bytes=)` 로 전달.
- 의존: `compare_panel._CaseSlot` (비교패널 복사로 충족), `evaluation_panel.set_layout_pixmap` (팀원 버전 채택으로 충족).

### 3-6. 프로젝트 설정 변경 시 공정표 즉시 갱신
- 프로젝트 설정 모달 확인 후, `self._tab_schedule.apply_project_settings(self._project_settings)` 호출 추가(예외는 dprint). 팀원이 `schedule_panel.apply_project_settings` 를 신설했으므로(§C) 연결.

### 3-7. 공정표 자동주입 — scene 인자 보완
- 우리는 `_on_tab_changed` 의 공정표 블록에서 `self._tab_schedule.on_enter(comps, self._project_settings)` 위임 구조를 쓴다(팀원은 main 에서 직접 `build_scene_data` 호출).
- 팀원이 `build_scene_data` 에 `scene` 인자(접합부 카운트 정확화용)를 추가했다. `scene=None` 기본값이라 **안 넘겨도 죽지는 않지만, 접합 수치가 fallback 으로 부정확**해진다.
- **보완**: `schedule_panel.on_enter` 시그니처를 `on_enter(scene_components, project_settings, scene=None)` 로 확장하고, 내부 `build_scene_data(..., scene=scene)` 로 전달. main 의 공정표 블록 호출을 `on_enter(comps, self._project_settings, self._scene)` 로 변경.

## 5. 보류 항목의 향후 처리 — "공용함수 리팩터링 재적용" 절차 (확정)

§1-B 에서 팀원 버전을 통째로 채택하므로, 우리가 했던 "공용 모듈로 추출" 리팩터링은 일단 **적용하지 않고 팀원 인라인 중복을 그대로 둔다**(기능 동일, 안전 우선). 향후 병합이 안정된 뒤 아래 절차로 재적용한다. **기능상 필수가 아니라 코드 중복 정리 목적**이며, 무심코 하면 깨지는 함정이 있으므로 절차를 고정한다.

### 5-1. `evaluation/evaluation_adapter.py`
1. 상수 `_MODULE_FLOOR_HEIGHT_MM = 3000.0` (67행)과 함수 `_module_floor_span(...)` 정의(70~76행)를 **통째로 삭제**.
2. 파일 상단에 `from modular_3d._utils.geometry import module_floor_span as _module_floor_span` 추가.
3. 사용처(`spans = [_module_floor_span(c) ...]` 등)는 이름이 같으므로 **그대로 둔다**.
4. **안전 근거**: 이 파일에서 `_MODULE_FLOOR_HEIGHT_MM` 은 함수 내부(74행)에서만 쓰임 → 함수와 함께 제거해도 잔여 참조 없음.

### 5-2. `schedule/schedule_adapter.py` (★ 함정 주의)
1. 함수 `_module_floor_span(...)` 정의(119~129행)만 삭제.
2. `from modular_3d._utils.geometry import module_floor_span as _module_floor_span, MODULE_FLOOR_HEIGHT_MM` 추가.
3. **상수 `_MODULE_FLOOR_HEIGHT_MM = 3000.0` (116행)은 단순 삭제 금지** — `_categorize_joints_by_rule(scene, floor_height_mm=_MODULE_FLOOR_HEIGHT_MM)` (216행)의 **시그니처 기본값으로도 쓰이기 때문**. 처리: 216행의 `_MODULE_FLOOR_HEIGHT_MM` 을 공용 `MODULE_FLOOR_HEIGHT_MM` 으로 치환한 뒤 116행 상수 줄을 삭제.
4. 사용처(484·625행)는 이름 동일 → 그대로.

### 5-3. `ui/evaluation_panel.py`
1. 함수 `_won(n)` 정의(240~241행)를 삭제.
2. `from modular_3d._utils.format import won as _won` 추가.
3. 사용처 13곳(`_won(...)`)은 이름 동일 → 그대로.
4. **안전 근거**: 우리 공용 `won` 은 `f"{int(round(float(n))):,}원"`, 팀원 `_won` 은 `f"{int(round(n)):,}원"` — `round()` 가 int/float 모두 받으므로 결과 동일.

## 8. 운영상 주의점 (코드 호환과 별개로 실수 가능한 부분)

1. **main_3d 는 자동 병합 불가 — 수동 이식**. 팀원 변경은 팀원 라인번호 기준이고 우리 main_3d 는 1326줄 달라 위치가 다르다. §3 항목을 우리 메서드(`_on_evaluation_save_case`·`_on_tab_changed`·프로젝트설정 적용부)에 **손으로** 끼워 넣어야 한다. 다행히 우리 평가 탭 진입 블록에 이미 동일 수집 코드가 있어 저장 패치는 복사 수준.
2. **공정표 HTML 과 schedule_adapter 는 한 세트 — 반드시 함께 가져온다**. 어댑터가 만드는 dict 키를 HTML JS 가 소비하므로, 둘 중 하나만 가져오면 키 불일치로 표가 빈다. (`apply_project_settings`·`apply_scene_data` 의 JS 도 HTML 의 `selectDate`/`onRegionChange`/`calc`/`render접합현황`/`REGION_GADONG` 함수 존재를 전제 → 팀원 HTML 에 포함)
3. **정적 분석이 보장 못 하는 것 = "데이터가 실제로 채워지는가"**. 시그니처·구조는 호환 확인했으나, 평가 자재비 표·공정표 접합 카운트가 비어 보이지 않는지는 **GUI 실행으로만** 확인된다. (학습·실행은 사용자가 직접 수행하는 정책)
4. **팀원코드 폴더 삭제는 맨 마지막**. 병합·검증이 끝나 안정화된 뒤 `modular_3d/팀원코드/` 를 통째로 지운다. 그 전엔 원본 대조용으로 남겨둔다.
5. **인코딩/줄바꿈**: 양쪽 같은 저장소(UTF-8) 라 복사 파일은 동일. 부분 병합하는 4개 파일은 우리 기존 파일을 Edit 하므로 인코딩 유지. (git 의 LF↔CRLF 경고는 기존부터 있던 것으로 동작 무관)
