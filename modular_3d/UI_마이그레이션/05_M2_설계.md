# M2 — three.js 표시 전용 뷰 설계

작성: 2026-05-28
대상: 모듈정의·배치설계 탭의 좌 3D 영역에 *읽기 전용* three.js 뷰를 추가.
방식: Strangler Fig — 기존 vispy 위에 새 three.js 뷰를 *세로 분할* 로 동시 마운트.

---

## 핵심 결정 사항

### 1. 신설 클래스 `ViewerThree` 의 인터페이스를 `Viewer3D` 와 *완전 동일* 하게

`Viewer3D` 의 시각 관련 메서드 (`add_component_visual`, `remove_component_visual`, `update_ghost`, `show_snap_markers` 등) 를 *같은 시그니처* 로 미러링한다. Controller 와 main_3d 의 *기존 호출 코드 한 줄도 안 건드리고* 같은 호출을 두 뷰어 모두에게 보낼 수 있게 한다.

이게 가능한 이유: 호출 인자가 모두 `(vertices, faces, face_colors)` 형태의 numpy array. 이 데이터는 *렌더러 무관* — vispy 도 three.js 도 같은 데이터로 그릴 수 있다.

### 2. 구현 방식 — QWebEngineView + HTML 인라인 + JS runJavaScript

운송탭 `loaded_3d_three.py` 의 패턴 그대로 재사용:
- HTML 템플릿에 Three.js + OrbitControls + (필요 시 CSS2DRenderer) 를 CDN 으로 로드
- QWebChannel 로 Python ↔ JS 양방향 통신 (M2 단계는 단방향 — Python → JS 만)
- `view.page().runJavaScript("addComponent(...)")` 호출로 JS 함수 실행
- BufferGeometry 사용 — vertices/faces/face_colors 를 JS Array 로 직렬화 후 setAttribute

### 3. 좌표계·단위 정책

| 영역 | x | y | z | 단위 |
|---|---|---|---|---|
| Python (Scene) | 길이 | 폭 | 높이 | mm |
| vispy (Viewer3D) | 길이 | 폭 | 높이 | mm (직접) |
| three.js (운송탭) | 오른쪽 | 위 | 화면쪽 | m (Python xy↔Three xz, mm→m) |
| three.js (ViewerThree) | **Python 과 동일** (x=길이, y=폭, z=높이) | mm |

**중요**: ViewerThree 는 *vispy 와 같은 좌표·단위* 를 쓴다. 운송탭의 y↔z 교환·mm→m 환산은 *적용 안 함*.
이유: Strangler 비교 시 두 뷰의 시각이 *직접 비교 가능* 해야 사용자 spot-check 효율 ↑.
three.js 의 카메라 up 벡터를 `(0, 0, 1)` 로 두고 z=높이 컨벤션 유지.

### 4. 색상 정책

`face_colors` 가 per-face 인 numpy float (R,G,B,A) 0~1. three.js BufferGeometry 는 per-vertex color 만 지원하므로:
- 각 face 의 3 꼭짓점에 같은 색 부여 (vertex 분리 — `setIndex(null)` 사용 또는 non-indexed)
- 또는 그룹별 머티리얼 분리 (face 가 같은 색끼리)

선택: **non-indexed BufferGeometry + per-vertex color**. 단순하고 vispy 와 시각 동일.

### 6. 카메라

three.js `PerspectiveCamera` + `OrbitControls`. vispy `CustomCamera(TurntableCamera)` 의 동작 (회전·줌·팬·커서 줌) 을 OrbitControls 기본값으로 근사. 정확한 일치는 사용자 spot-check 영역.

초기 카메라 파라미터: distance=20000, fov=45, elevation=30, azimuth=-60, center=(3000, 3000, 0), up=(0, 0, 1) — Viewer3D 와 동일.

### 7. Strangler 마운트 정책

배치 탭·정의 탭의 좌 3D 영역에:

```
기존 좌 3D 영역 (Viewer3D.canvas_widget)
       ↓
세로 QSplitter (Vertical)
├── 상: Viewer3D.canvas_widget   (기존 vispy)
└── 하: ViewerThree.web_view     (새 three.js)
```

초기 비율 1:1. 사용자가 핸들로 자유 조정.

배치 탭은 *MainWindow 가 공유 Viewer3D* 를 가지므로 *MainWindow 가 공유 ViewerThree 도 한 개* 보유. 정의 탭은 *자체 Viewer3D* 를 가지므로 *자체 ViewerThree 도 별도* 보유 (두 탭이 독립 작업공간).

### 8. Controller hook 정책

`Controller.add_component_visual` 같은 메서드는 *없음* — Controller 가 `self._viewer.add_component_visual(...)` 형태로 *Viewer3D 인스턴스에 직접 호출*. M2 에선:

- Viewer3D 와 ViewerThree 를 *모두 가진 어댑터 클래스* `ViewerStrangler` 신설
- 같은 시그니처의 모든 메서드에서 *두 뷰어 모두 호출* (broadcast)
- Controller 가 받는 `viewer` 인자를 `ViewerStrangler` 인스턴스로 교체

이러면 *Controller 내부 한 줄도 안 건드림*. 어댑터가 자동으로 두 뷰어 갱신.

### 9. 빈 메서드 (NotImplementedError 안 던지기)

ViewerThree 에 *해석·운송 관련 메서드* (show_slab_overlay 등) 는 *no-op* 으로 둔다. ViewerStrangler 가 두 뷰어 모두 호출할 때 ViewerThree 에서 AttributeError 안 나도록 *전부 정의*. 단 본문은 비어있음.

## 위험 / 한계

1. **Three.js CDN 의존** — 운송탭과 동일. 오프라인 환경 고려 시 번들 필요 (M2 범위 외).
2. **per-vertex color 의 성능** — 부재 수 100+ 일 때 BufferGeometry 빈번 갱신이 느릴 가능성. 측정 후 필요시 InstancedMesh 등 최적화.
3. **OrbitControls vs CustomCamera 동작 차이** — 사용자 체험 영역. 마이그레이션 후 spot-check 으로 튜닝.
4. **Python ↔ JS 비동기성** — `runJavaScript` 가 비동기. 빠른 연속 add/remove 시 순서 보장이 필요하면 콜백 체인 또는 JS 측 큐.
