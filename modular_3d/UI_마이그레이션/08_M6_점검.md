# M6 — 편집 모드 전체 이관 점검

작성: 2026-05-28
목적: M4·M5 로 three.js 2D 가 입력 주체가 된 뒤, 시나리오 카탈로그(03)의
모든 편집 입력이 three.js 경로로 빠짐없이 동작하는지 점검. 누락 보완.

---

## AlignmentCanvas 입력 이벤트 → three.js 경로 매핑 (완전성)

AlignmentCanvas 의 *모든* Qt 입력 이벤트 핸들러와 그 three.js 대응:

| Qt 이벤트 핸들러 | three.js 경로 | 상태 |
|---|---|---|
| `mousePressEvent` (좌/우클릭) | JS mouseup → `bridge.on_2d_click` → `handle_world_click` → `_process_press_at` | ✓ M4 |
| `mouseMoveEvent` (호버·미리보기 추종) | JS mousemove → `bridge.on_2d_move` → `handle_world_move` → `_process_move_at` | ✓ M4 |
| `keyPressEvent` (배치·정렬·편집 키) | JS keydown → `bridge.on_2d_key` → `handle_key` → `_process_key` | ✓ M5 |
| `mouseReleaseEvent` (MiddleButton 팬 종료) | three.js 자체 팬 (vispy 무관) | ✓ M4 자체 |
| `wheelEvent` (줌) | three.js 자체 커서기준 줌 | ✓ M4 자체 |
| `resizeEvent` (auto-fit) | JS `onResize` + `_applyCamera` | ✓ M3/M4 |
| `paintEvent` (표시) | `_collect_paint_state` → `applyPaintState` | ✓ M3 |

**더블클릭·우클릭메뉴·드래그앤드롭·enter/leave 등 추가 핸들러 없음** (확인 완료).
→ AlignmentCanvas 의 입력 표면(surface)이 *전부* three.js 경로로 커버됨. 누락 0.

---

## 입력 처리 로직 공유 구조 (선택 알고리즘 0줄 신규)

핵심 — vispy 와 three.js 가 *같은 처리 메서드* 를 공유:

```
mousePressEvent(event) ─┐
                        ├→ _process_press_at(mx, my, button)   ← 선택·실·개구부·배치확정·정렬
handle_world_click ─────┘   (world→screen 왕복 항등)

mouseMoveEvent(event) ──┐
                        ├→ _process_move_at(mx, my)   ← 호버·미리보기 추종
handle_world_move ──────┘

keyPressEvent(event) ───┐
                        ├→ _process_key(key, text)   ← 배치 1~9·X/Y·R/V·M/C·Z·Del·Enter·Esc
handle_key ─────────────┘   (JS key → Qt.Key_* 매핑)
```

즉 *선택·정렬·배치·편집 알고리즘은 한 줄도 새로 안 짰다*. 기존 분기를 메서드로
추출해 두 입력원이 공유. 단일 AlignmentCanvas 상태 유지 → vispy·three.js 동기.

## 시나리오 카탈로그(03) A 섹션 커버리지

| 시나리오 군 | three.js 동작 | 경유 |
|---|---|---|
| A.1 컴포넌트 선택·정렬·삭제·이동·복사 | ✓ | click + key (1~9/X/Y/1~5/M/C/Del/Z/Esc) |
| A.2 실 모드 (그리기·선택·이동·복사) | ✓ | click(좌/우) + key (Enter/Esc/M/C/R/Del/V) |
| A.3 개구부 모드 | ✓ | click + key (R/V/Del/M/C/Esc) |
| A.4 정의 가져오기 그룹 | ✓ | move + click + key (R/V/Esc) |
| A.5 DockPanel 상단 (층수·저장·불러오기) | ✓ | Qt 네이티브 위젯 (three.js 무관, 그대로) |
| A.0 뷰포트 (줌·팬) | ✓ | three.js 자체 카메라 |

치수 입력(DimensionInputPanel)·팔레트·우측 속성 패널은 *Qt 네이티브 위젯* 이라
three.js 마이그레이션 대상이 아니며 시그널로 그대로 연결됨.

## 정의 탭 / 배치 탭 동일 적용 확인

- 배치 탭: `MainWindow._f5_panel_three.attach_to(self._f5_panel.canvas)` (M3-b)
- 정의 탭: `DefineTab._f5_panel_three.attach_to(self._f5_panel.canvas)` (M3-b)
- `attach_to` 가 `set_input_callbacks(on_click/on_move/on_key)` 등록 (M4-b/M5-a)
- 두 탭 모두 *같은 AlignmentCanvas 클래스* 사용 → `handle_world_click`/`move`/`key`
  동일 보유 → 자동 커버.

## 결론

M4·M5 로 입력 진입점 3개(click/move/key)를 공유화한 결과, **AlignmentCanvas 의
모든 편집 시나리오가 three.js 입력으로 자동 커버**됨. M6 에서 별도 신규 구현 불필요.
누락 0 확인.

남은 것:
- **사용자 spot-check** — 정의 탭·배치 탭 양쪽에서 three.js 만으로 전체 편집
  플로우(배치→정렬→이동→삭제→실→개구부)가 vispy 와 동일 결과인지.
- M7 (Strangler 비교 검증) 에서 종합 점검.

## 알려진 한계 (M7/M8 에서 다룸)

1. **이중 입력 경로** — vispy 캔버스도 여전히 입력 받음 (Strangler 단계). M8 에서
   vispy 제거 시 단일화.
2. **카메라 독립** — three.js 2D 시점이 vispy 와 따로 (사용자 수용, vispy 제거 예정).
3. **포커스** — three.js 캔버스 키 입력은 클릭으로 포커스 후 작동.
