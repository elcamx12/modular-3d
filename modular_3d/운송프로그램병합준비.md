## 분석 ① — 인풋 매핑

### 1. 운송프로그램이 받는 인풋 전수 (`src/models.py` 기준)

운송프로그램의 5대 데이터클래스:
- **Section** (강재 단면): `name, section_type(SHS/RHS/H/C/L/CFT), width, height, thickness, weight_per_m, flange_thickness`
- **Module**: `name, width, length, height, column_section, beam_section, extra_weight_kg`
  - `weight`는 프로퍼티 — 프레임 강재(4 기둥+8 보) + `extra_weight_kg`(슬래브+비내력벽) 합산
- **Panel** (`kind ∈ {floor, wall, lshape}`): `name, kind, width, length, thickness, beam_section, column_section?, wall_height, extra_weight_kg`
  - floor: 둘레 보 4개
  - wall: 보 2(위·아래) + 기둥 2(양쪽)
  - lshape: 보 5 + 기둥 2 + `wall_height`
- **Truck**: `name, truck_type(lowbed/extendable/aframe), max_length, max_width, max_height, max_weight, vehicle_height_offset, hourly_rate_krw`
- **RoadClass**: `name, max_length, max_width, max_height, max_weight`
- **SpacingParams**: `panel_gap_mm(=100), truck_edge_clearance_mm(=200), lshape_stack_gap_mm(=100)`

### 2. 우리 프로그램이 이미 가지고 있는 데이터

- **씬 컴포넌트** (`model/core.py`): `Module / FloorPanel / StructWall / Vertical3Module / Core / CoreSlab / CantileverBeam / CantileverSlab / MidBeam / MidColumn`
  - 각각 `dimensions['width','depth','height']` (mm), `position`, `rotation`, `anchor`
- **단면 산정 결과** (`analysis/section_design.py` → `DesignResult`):
  - 정책별 그룹(1종 all_steel / 2종 columns·beams / 3종 columns·beams·cantilevers) → 채택 `SHSSection`
  - 층구간 분할 시 `columns_F1_3`, `columns_F4` 식으로 그룹 세분화
  - `SHSSection`: `name, weight_per_m_kg, A, I, ...` (SHS 한 종류만)
- **하중 계산** (`analysis/load_calculator.py`): 슬래브 자중·DL·LL을 둘레 보에 N/mm UDL로 분배
- **물량 집계** (`analysis/quantity_takeoff.py`): 슬래브 부피(m³)·철근 추정 중량, 강재 본수표

### 3. 매핑표 — "우리 결과 자동 주입 가능 / UI 입력 필요"

#### (A) Module → 운송 `Module`

| 운송 필드 | 우리 데이터 | 자동/UI | 비고·이슈 |
|---|---|---|---|
| `name` | `comp_meta` 라벨 (`"a모듈"` 등) | 자동 | 구조해석탭 라벨 그대로 재사용 |
| `width` | `Module.dimensions['width']` | 자동 | 단위 동일(mm) |
| `length` | `Module.dimensions['depth']` (Y방향) | 자동 | **이름 충돌 주의** — 우리는 depth, 운송은 length |
| `height` | `Module.dimensions['height']` | 자동 | |
| `column_section` | `DesignResult.member_to_group[기둥mid]`→`section` | 자동 (정책·층구간 선택 후) | **이슈 1·2 참조** |
| `beam_section` | 같은 방식으로 모듈보 그룹 단면 | 자동 | 1종/2종/3종 어느 정책을 쓸지 UI 결정 |
| `extra_weight_kg` | 슬래브 자중(부피×2400kg/m³) 단독 계산 가능. 비내력벽 채움재는 없음 | **반자동** | 슬래브는 우리 부피로, 채움재는 UI 입력 또는 0 |

#### (B) FloorPanel → 운송 `Panel(kind="floor")`

| 운송 필드 | 우리 데이터 | 자동/UI | 비고 |
|---|---|---|---|
| `width / length` | `dimensions['width','depth']` | 자동 | |
| `thickness` | **슬래브 두께 + 보 단면 높이** 동시 고려 — 운송 두께는 max(슬래브, 보 단면 H) 또는 슬래브+보 적층 도식 기준 | 반자동 | **이슈 4 — 사용자 정정 반영**. `SlabData.thickness=150`은 시각화용(`SLAB_THICKNESS_MODEL_MM`)일 뿐, 실제 OpenSees 자중은 `SLAB_THICKNESS_MM=200` 기준으로 계산됨(`load_calculator.py:344`). 운송 두께는 보 단면 두께(예 SHS 200×200×8 → 200mm)와 슬래브 두께를 함께 고려해야 함 |
| `beam_section` | `floor_panel_beam` 그룹 단면 | 자동 | |
| `extra_weight_kg` | 슬래브 자중 = `SLAB_THICKNESS_MM(=200)` × 면적 × `CONCRETE_UNIT_WEIGHT` — **OpenSees가 쓰는 값과 동일하게** | 자동 | 모듈과 동일 방식 |

#### (C) StructWall → 운송 `Panel(kind="wall")`

운송 wall Panel 정의: 위·아래 보(=2×length 방향), 양쪽 기둥(=2×width 방향). 즉 width=층고, length=벽 길이.

| 운송 필드 | 우리 데이터 | 자동/UI | 비고 |
|---|---|---|---|
| `width` | `StructWall.dimensions['height']` (벽 높이=층고) | 자동 (회전 매핑) | **이슈 5** — 축 회전 필수 |
| `length` | `StructWall.dimensions['width']` (벽 길이) | 자동 (회전 매핑) | |
| `thickness` | `StructWall.dimensions['depth']` (=200) | 자동 | |
| `beam_section` | `wall_panel_beam` 그룹 단면 | 자동 | |
| `column_section` | `wall_panel_column` 그룹 단면 | 자동 | |
| `wall_height` | (불필요, wall엔 0) | — | lshape 전용 |
| `extra_weight_kg` | 벽체 채움(`WallPanelData.thickness`×면적×채움재밀도). 채움재 밀도는 우리 데이터에 없음 | **UI** | 단열·마감재 종류·밀도 UI 입력 |

#### (D) Vertical3Module / Cantilever / Core / CoreSlab — 매핑 정책 결정 필요

- **Vertical3Module — 옆으로 눕혀서 운송 (사용자 정정 반영)**: 높이 ≈ 10,260 mm (3층×3,420). 자르지 않고 **눕혀서 운송**. 눕힐 때 회전 매핑:
  - 운송 `length` = 원래 `height` (10,260) → 광로 `max_length=19,000` 내 OK
  - 운송 `height` = 원래 `width` (예 3,400) → 광로 `max_height=4,500` 내 OK (단 `width ≤ 4,500` 만족 필수)
  - 운송 `width` = 원래 `depth` (6,820) → **광로 폭 3,500 초과 → NG**. 짧은 변(width)을 위로 두고 긴 변(depth)을 폭 방향으로 둘 수 없음. **결국 눕히는 방향은 width를 위로, depth를 길이 방향으로** 두는 것이 유일한 해 — 그러면 width=depth(원), length=height(원). 어댑터 함수에서 명시 매핑 필요.
- **CantileverBeam / CantileverSlab**: 본 모듈에 부착되어 출하되는지(=부모 모듈에 흡수) 별도 출하되는지 사용자 판단 필요. **UI 입력으로 정책 토글** 권장.
- **Core / CoreSlab**: RC 현장 타설이므로 운송 대상 제외. `aggregate_steel`이 이미 CAT_RC_CORE를 강재 본수표에서 빼고 있음과 동일 정책 — 운송 매핑에서도 **명시적 제외 필수**.
- **MidBeam / MidColumn**: 모듈 내부 보강재. 부모 모듈에 흡수돼 함께 운송된다고 보는 것이 합리적 — 단, 우리 `extra_weight_kg`에 강재 자중으로 가산 필요(이중계산 주의).

#### (D-2) 다면 종속 패널 — 우리 데이터 매핑 (사용자 정정: L자만이 아니라 ㄷ자·3면 포함)

운송 측 `Panel(kind="lshape")`은 벽 1면 종속만 지원. 우리는 0/1/2/3 면 모두 발생 가능 → **운송 측 데이터모델·패커·시각화 모두 다면 지원으로 확장**.

분기 로직:
- `FloorPanel.merged_wall_ids` 길이로 분기 (0 → floor / 1 → lshape / 2 → lshape2(ㄷ자) / 3 → lshape3)
- 독립 `StructWall` (`merged_fp_id is None`) → `kind="wall"` 그대로

| 필드 | 우리 데이터 | 비고 |
|---|---|---|
| `width / length` | 부모 `FloorPanel.dimensions['width','depth']` | 자동 |
| `thickness` | 슬래브 150 (통일 후) + 보 단면 H 동시 고려 | 자동 |
| `beam_section` | `floor_panel_beam` 단면 + 종속 벽 보는 `wall_panel_beam` | 자동 |
| `column_section` | 종속된 각 `StructWall`의 `wall_panel_column` 단면 (벽마다 동일 단면 가정) | 자동 |
| 벽 스펙 리스트 | 종속된 각 `StructWall`의 `dimensions['width','height']` 와 부재 단면 — **벽 N면을 지원할 수 있도록 운송 측 `wall_height` 단일 필드를 `walls: List[WallSpec]` 로 확장 필요** | 신규 데이터모델 |
| `extra_weight_kg` | 바닥슬래브(150) 자중 + 벽 채움재(UI 입력) | 반자동 |

→ **이슈 7 해결**: 분기 로직 + 다면 데이터모델 확장 2가지 작업. 운송 패커·시각화·_can_stack 검사도 함께 확장.

#### (F) Section 카탈로그 — `data/sections.json` ↔ `analysis.SHS_CATALOG`

운송 측은 SHS/RHS/H/C/L/CFT 6 종 모두 있지만, 우리는 **SHS만 사용**. 우리가 채택한 단면을 운송 `Section`으로 변환할 때는:
- `section_type="SHS"` 고정
- `width = height = SHSSection.size`
- `thickness = SHSSection.thickness`
- `weight_per_m = SHSSection.weight_per_m_kg`
- `flange_thickness = 0.0`

→ **런타임 변환 어댑터 함수 한 개로 충분**. `data/sections.json`을 통째로 가져올 필요 없음(우리 카탈로그가 단일 진실원).

### 4. 자동 매핑 7대 이슈 — 사용자 피드백 반영 후 결론

1. **정책 다중성** → **물량탭의 최종 선택값을 운송탭이 그대로 받는다**. 구조해석탭의 정책 라디오가 1차 선택, 물량탭에서 사용자가 확정한 정책(+ 층구간 분할 수치)이 운송탭 입력의 단일 진실원. 운송탭에서 정책을 다시 고르게 하지 않는다.
2. **층구간 분할 시 단면 분기** → **층마다 단면이 다르면 다른 모듈로 취급**. 같은 평면이라도 `columns_F1_3`에 속한 1~3층 모듈과 `columns_F4`에 속한 4층 모듈은 운송에서 별개 모듈 인스턴스(이름·단면 다름). 어댑터 함수에서 모듈 인스턴스 ID에 층 정보를 묶어 키 생성.
3. **모듈 weight 이중계산** → **정책 명확화**:
   - 운송 `Module.weight` = (운송 측 자동 계산하는 4기둥+8보 프레임 강재) + `extra_weight_kg`
   - `extra_weight_kg`에 들어가야 할 것: 슬래브 자중(OpenSees와 동일 두께·밀도 기준) + 슬래브 철근 + 비내력벽 채움재(있으면) + MidBeam/MidColumn 자중
   - **이중계산 회피**: 프레임 4기둥+8보는 운송 측이 자동 계산하므로 우리는 그 부분을 `extra_weight_kg`에 넣지 않는다. 어댑터 단위 테스트로 "운송 측 자동 합산값 = OpenSees 자중 합산값" 일치 검증.
4. **FloorPanel 두께 + 슬래브 자중** (사용자 정정 — 2026-05-19 통일 완료):
   - `SLAB_THICKNESS_MODEL_MM`(시각)과 `SLAB_THICKNESS_MM`(해석)을 **모두 150 으로 통일** (`카탈로그/geometry.py` 변경 완료). 자중 계산도 150 기준.
   - **운송 두께는 슬래브 단독이 아니라 보 단면 높이(예 SHS 200)와 함께 고려해야 함** — 적층 시 보가 슬래브 아래에 매달리는 형상이므로 실제 적층 단위 두께 = 슬래브 두께(150) + 보 단면 H 일부 또는 max(150, 보H).
   - **슬래브 자중은 통일된 150 mm × 콘크리트 단위중량** 으로 계산 (해석·시각·운송 동일 진실원).
5. **StructWall 축 회전 매핑** → **변수명 충돌은 어댑터 단계에서 명시 회전 또는 운송 측 코드의 변수명을 우리 컨벤션으로 리네임** 둘 중 택1 (필수는 아님 — 어댑터 명시 매핑이 충분). 오류 없도록 단위 테스트 필수.
6. **Vertical3Module — 자르지 않고 옆으로 눕혀서 운송** (사용자 정정):
   - 수직3모듈 실제 치수: 가로 3,400 × 세로 3,400 × 높이 12,000 이내 (사용자 명시).
   - 회전 매핑: 원래 `height(≤12,000)` → 운송 `length` (광로 19,000 ✓), 원래 `width(3,400)` → 운송 `width` (광로 3,500 ✓), 원래 `depth(3,400)` → 운송 `height` (광로 4,500 ✓).
   - 모든 도로 한도 통과 — 추가 광폭 허가 불필요.
7. **종속 패널 → 다면 패널 확장** (사용자 정정):
   - 운송 측은 `kind="lshape"` (벽 1면 종속) 만 정의.
   - 우리는 `FloorPanel.merged_wall_ids`에 합체된 벽 개수가 0/1/2/3 모두 가능 → **L자(1면), ㄷ자(2면), 3면 종속(3면) 모두 발생**.
   - **확장 필요**: 운송 측 `kind` 에 `lshape2`(ㄷ자), `lshape3`(3면) 추가하거나, `wall_height` 만 두지 말고 `walls: List[wall_spec]` 같은 다중 벽 스펙으로 일반화. `Panel` 데이터클래스 + `_can_stack_on_lshape` + `_pack_lshape_panels` + visualizer 모두 확장 대상.
   - **종속되지 않은 벽패널** (`StructWall.merged_fp_id is None`) → 운송 측 `kind="wall"` (눕혀서 적층 운송) 그대로 사용.
   - 변환 분기:
     · `FloorPanel.merged_wall_ids == []` → `kind="floor"`
     · `len == 1` → `kind="lshape"` (운송 측 기존 매핑)
     · `len == 2` → `kind="lshape2"` (신규)
     · `len == 3` → `kind="lshape3"` (신규)
     · 독립 `StructWall` → `kind="wall"`

### 5. 자동 vs UI — 한 줄 요약 (피드백 반영본)

- **자동 주입 가능**: Module/FloorPanel/StructWall 치수·단면(물량탭 최종 선택 정책 + 층구간 분할 기준), 모듈/플로어 슬래브 자중(OpenSees 동일 두께·밀도), 합체 벽-바닥 → L자 패널, Vertical3Module → 눕힌 1매 모듈.
- **UI 입력 필수**: 비내력벽 채움재 밀도, 캔틸·코어 운송 정책 토글, 트럭 카탈로그·도로 등급·간격 파라미터·운임.
- **UI 비노출**: 정책 선택(물량탭에서 이미 확정됨), L자 패널(합체 데이터로 자동 생성).

## 분석 ② — 운송프로그램 자체 버그·로직 정합성 점검

운송 측 핵심 코드 4개 (`src/models.py`, `src/packer.py`, `src/limits.py`, `src/visualizer.py`)와 데이터 (`data/trucks.json`, `data/road_limits.json`)를 정독해 발견한 결함을 심각도별로 분류.

### 🔴 심각 (병합 전 반드시 수정)

**B-1. 도로 한도 중량 해석 오류 (`src/limits.py:can_carry`)**

`weight_lim = min(truck.max_weight, road.max_weight)`로 두 한도를 무차원 동일 단위로 묶고 화물 무게만 비교. 그러나 `road.max_weight=40,000(광로)`는 **차량+화물 총중량(GVW)** 기준이고 `truck.max_weight=25,000(25t 카고)`은 **화물만** 기준. 두 값을 같은 차원으로 묶으면 안 됨. 예: 광로 40t 한도 ≠ 트럭 25t 한도 — 광로는 차량 자체(공차 10~15t) 포함이므로 화물 한도는 25~30t가 실효. 현재 코드는 늘 트럭 한도가 작아 우연히 안전 측이지만, 도로 한도가 더 작은 케이스(이면도로 15t)에서 차량 공차 무시로 **과다 적재 허용 위험**.

→ 수정 방향: `road.max_weight - truck.curb_weight` 로 화물 한도 환산 후 `min` 비교. `Truck`에 `curb_weight_kg` 필드 추가 필요.

**B-2. `_can_stack_on_lshape` 폭 검사 — 벽 두께 vs 바닥판 두께 혼선 (`src/packer.py`)**

`avail_w = lshape.width - lshape.thickness - sp.lshape_stack_gap_mm`에서 `lshape.thickness`를 **벽체 두께**로 사용. 그러나 `models.py:Panel.thickness` 주석은 "플로어: 슬래브 두께 / 벽체·L자: 벽체 두께"로 의도는 벽체 두께. 반면 `visualizer.py:draw_rear_view`의 L자 단면 그리기에서는 `cursor_y + sample.thickness`로 **바닥판 두께**로 사용 (벽체는 `wall_thick_vis = sample.thickness`로 같은 값을 다시 가져다 씀 → 결국 바닥판 두께 = 벽체 두께 가정).

L자 패널 데이터모델이 **바닥판 두께와 벽체 두께를 동일 필드 `thickness` 하나로 묶어버린 것이 근본 버그**. 우리 데이터는 슬래브 두께(150) ≠ 벽체 두께(200~)이므로 그대로 매핑 불가.

→ 수정 방향: `Panel`에 L자 전용 `floor_thickness, wall_thickness` 분리 필드 추가. `_can_stack_on_lshape`·시각화·`_max_lshape_panels_per_truck` 모두 두 두께 분리 참조.

**B-3. L자 위 적층 무게가 `_max_lshape_panels_per_truck`에 누락**

`_max_lshape_panels_per_truck`는 적층 없는 가정으로 `n_wt = floor(max_weight / panel.weight)` 만 계산. 실제 `_pack_lshape_panels`는 적층 패널을 추가하지만 무게 한도 가드는 `b["total_weight"] + cand.weight > b["truck"].max_weight` 한 곳뿐 — `recheck_trip_with_truck`에서 트럭 교체 시 적층 무게가 무시되는 경로가 있음 (`_max_lshape_panels_per_truck` 호출만 함).

→ 수정 방향: `recheck_trip_with_truck`의 lshape 분기에서 `n*sample.weight` 가 아니라 `sum(items.weight) + sum(stacked.weight)` 로 총합 계산.

### 🟡 보통 (병합 전 검토)

**B-4. A-frame 트럭 데이터가 코드 전 분기에서 미사용 (`src/packer.py`)**

`_wall_panel_compatible_trucks` 가 `lowbed/extendable` 만 허용해 A-frame 트럭이 packing 후보에 절대 안 들어감. `data/trucks.json`에 `aframe` 정의는 있지만 데드데이터. 의도가 "벽패널을 눕혀 적층으로 통일"이라면 A-frame 트럭 정의를 데이터에서 삭제하거나, A-frame 전용 분기(`_pack_wall_panels_aframe`)를 복구해야 함.

**B-5. `_pack_floor_panels` ppr 고정 — 혼적 시 비효율**

첫 패널 기준 `ppr`을 정한 뒤 이후 다른 사양 패널을 추가할 때 `ppr` 재계산 없음. 더 짧은 패널이 들어오면 트럭 길이를 다 못 채움. FFD 빈팩 정확성에는 영향 없으나 적재율 손실.

**B-6. 도로 등급 4 종 한도가 모두 동시에 화물 한도로 사용됨 (`limits.py`)**

`length_lim = min(truck, road)` 등 4 항목 모두 `min` 합성. 실무에서 도로 한도는 "허가 면제 한도" 일 수 있고, 광폭 운송 허가 받으면 초과 가능. 운송프로그램에 이 우회 입력이 없음. 추후 광폭 허가 케이스 처리 필요.

**B-7. `simulate_manual_trip`에서 wall panel을 floor 분기로 위임**

`recheck_trip_with_truck`의 wall 분기가 `_max_floor_panels_per_truck` 호출. 두 종류 패널 적층 정책이 코드상 동일하지만 분리 함수가 없어 의미가 불투명. 리팩토링 권장.

### 🟢 경미 (참고)

**B-8. `_panel_overcount_reason`의 `nl·ppr` 계산 분기 — 가장자리 케이스에서 오메시지**

`nl = max(int(...), 1)` fallback이 두께 초과 시 1로 떨어져 `stack_h` 계산이 의도와 어긋날 수 있음. 단 호출 측 가드(`if panel.thickness > inner_h: return 0, ppr, 0`)로 nl=0 경로가 우선이라 실제 영향 없음.

**B-9. 3D L자 시각화 좌표 — 적층 패널 y 시작점**

`stk_cx = cy + item.thickness + sp.lshape_stack_gap_mm`에서 `item.thickness`가 벽체 두께라는 가정이 깨지면(B-2와 연동) 시각화도 어긋남.

**B-10. 모든 테스트가 `tests/test_can_carry.py` 8 케이스뿐 — packer 미커버**

`_pack_modules`, `_pack_floor_panels`, `_pack_lshape_panels`, `recheck_trip_with_truck` 등 핵심 로직에 단위 테스트 없음. 회귀 검증 어려움.

### 🔴 심각 — 2차 정독에서 추가 발견 (병합 전 반드시 수정)

**B-11. `Module.weight` 보 길이 계산식 — 2배 오버 버그** ★★★ (가장 심각)

`models.py:Module.weight` 의 보 총길이 계산:
- 코드 식: `beam_total_m = (4 * (self.width + self.length) * 2) / 1000.0` → `8(w+l)/1000`
- 실제 모듈 보: 천장 4개(둘레=2(w+l)) + 바닥 4개(둘레=2(w+l)) = 총 `4(w+l)`
- **코드값이 정확히 2배**. 검증 예: w=3,400 l=6,820 → 정답 40.88m, 코드 81.76m.

결과: 운송 측이 계산하는 **모듈 프레임 강재 자중이 정답의 2배**. 모듈 1매 총중량이 부풀려져 트럭 적재 한도 검사에서 **불필요하게 보수적**으로 판정 → 실제로는 실을 수 있는데도 NG·다른 트럭 강제 가능. 또한 app.py가 `frame_sample.weight` 를 그대로 표시하므로 사용자에게 잘못된 무게 출력.

→ 수정: `beam_total_m = (4 * (self.width + self.length)) / 1000.0` ((w+l)×2 둘레×2층 = 4(w+l)).

**B-12. 도로 길이 한도 — 트레일러 자체 길이 미포함** ★★

`limits.py:can_carry` 의 길이 검사: `length_lim = min(truck.max_length, road.max_length)` 후 화물 length만 비교. 실제 도로 한도는 **차량 총길이(트랙터+트레일러+화물)** 기준. 트레일러 자체 12m + 화물 9m = 21m 총길이지만 코드는 화물 9m와 도로 19m 비교 → 통과 판정. **이면도로(12m 한도) 같은 좁은 도로에서 과대 통과 위험**.

→ 수정: `Truck`에 `trailer_length_mm`(트랙터+트레일러 자체 길이) 필드 추가, 화물 length + trailer_length로 도로 한도 검사.

**B-17. 슬래브 두께·단위중량이 코드에 하드코딩 (UI 입력 불가)** ★★

`app.py`의 모듈 슬래브 자중: `slab_w = (w/1000)*(l/1000) * 350.0` (350 kg/m² 고정, "콘크리트 180mm").
플로어 패널: `FLOOR_SLAB_UNIT_WEIGHT = 350.0`.
- 사이드바·폼 어디에도 슬래브 두께·콘크리트 단위중량 입력 없음.
- 우리 슬래브 150mm 통일과 직접 충돌. 150mm × 2,400 kg/m³ = 360 kg/m² (가까운 값이지만 일관성 위해 사용자 입력화 필요).

→ 수정: `extra_weight_kg`를 우리 어댑터에서 계산해 넘김. app.py의 하드코딩 분기는 우리 GUI로 이식 시 제거.

**B-22. L자 패널 입력에서 슬래브 자중·비내력벽 누락** ★★★

`app.py:_lshape_form`은 `extra_weight_kg=0` 으로 고정. 표시도 "🪶 자동 산출 무게 (부재만)" 명시. 즉 L자 패널은 강재 프레임만 계산되고 **바닥 슬래브 + 벽 채움재가 전부 빠져 있음** → 실제보다 1,000~2,000kg 가볍게 운송 계산 → 적재 한도 검사 통과해 놓고 현장에서 과적 발생 위험.

→ 수정: floor/wall 폼과 동일하게 슬래브 자중 + 벽 비내력재 입력·합산.

### 🟡 보통 — 추가 발견

**B-13. `_can_stack_on_lshape` 길이 검사 기준 오류**

`if panel.length > usable: return False` 에서 `usable`은 트럭 적재 유효 길이. 그러나 적층 패널은 **베이스 L자 패널 위에** 올라가므로 베이스 L자보다 길면 베이스에서 튀어나옴. 정답 검사는 `panel.length > base_L.length`. 현재 코드는 베이스보다 긴 적층 허용 가능.

**B-14. L자 위 L자 적층 시 적층 L자 벽 두께 점유 미반영**

`_can_stack_on_lshape` 폭 검사는 `panel.width ≤ lshape.width - lshape.thickness - gap` 까지만 봄. 적층되는 패널이 L자면 그 자체 벽 두께가 또 추가로 점유하지만 미반영.

**B-23. `NONBEARING_WALL_TYPES` 와 `_NB_TYPES` 중복 정의**

사이드바·플로어 폼 등 두 군데에 같은 값(30/55 kg/m²) 별도 dict로 정의. 한쪽 변경 시 다른 쪽 동기 안 됨 → 유지보수 위험.

**B-25. `Trip.cargo_weight` ≡ `Trip.total_weight`**

두 프로퍼티가 같은 값 반환. 의미상 total은 차량 자체 + 화물이어야 하지만 차량 무게 미포함. 도로 GVW 한도(B-1, B-12) 검사도 못 함.

**B-27. 사이드바 "운행 가능 도로" 표 — 화물 미포함 판정**

차량 자체 max_length/max_width만 도로 한도와 비교. 화물·트레일러 합산 미고려. 사용자에게 "이 트럭은 이면도로 가능"이라고 잘못 안내 가능.

### 🟢 경미 — 추가 발견

**B-15. JSON 로더 데이터 검증 부재**

`Truck.truck_type: Literal[...]` 는 Python 런타임 검증 없음. `data/trucks.json` 오타 시 사일런트 실패.

**B-16. 시각화 함수에 화물 초과 가드 없음**

`cy = (truck.max_width - item.width) / 2` 에서 화물 폭 > 트럭 폭이면 cy<0 → 그림 깨짐. can_carry 통과 가정이지만 가드 없음.

**B-19. `_section_select` default 미존재 시 첫 단면(`SHS 50x50x3.2`) 사일런트 fallback**

`MODULE_DEFAULTS`·`WALL_DEFAULTS` 등의 단면명이 `sections.json`에서 사라지면 사용자 모르게 가장 작은 단면으로 fallback → 잘못된 무게.

**B-21. `pack_items` 미캐싱 — 입력 변경 시 매번 전체 재실행**

`@st.cache_data` 가 카탈로그 로드에만 적용. 큰 입력에서 사용자 입력 살짝 바꿔도 전체 packing 재실행.

**B-28. L자 패널 보·기둥 정의 모호**

`Panel.weight` lshape 분기 `col_total_m = 2 * wall_height` (벽 양쪽 기둥 가정). 그러나 주석은 "바닥 양옆 기둥"이라 정의 불일치.

## 분석 ③ — 가져올 기능 / 제외할 기능 분류

## 분석 ④ — 어댑터 변환 계약 명세 (A)

운송탭이 호출하는 단일 진입점: **`build_transport_input(scene, design_result, policy, options) → TransportInput`**.
이 함수 하나가 우리 씬·구조해석 결과를 운송 측 데이터모델(Module/Panel 리스트)로 변환하는 모든 책임을 진다.

### 1. 입력 계약

| 인자 | 타입 | 의미 | 결정자 |
|---|---|---|---|
| `scene` | `model.core.Scene` | 현재 씬 (사용자가 만진 모든 부재) | 우리 GUI 상태 |
| `design_result` | `Dict[str, DesignResult]` (`{'1종':…,'2종':…,'3종':…}`) 또는 단일 `DesignResult` | 정책별 단면 산정 결과. 층구간 분할 후처리 포함 | 물량탭 |
| `policy` | `str` (`'1종'/'2종'/'3종'`) | 운송탭에서 사용할 정책. **물량탭 최종 선택값** | 물량탭 → 운송탭 시그널 |
| `options` | `TransportOptions` 데이터클래스 | 사용자 토글 (캔틸 운송, 외부벽 단가, 비내력벽 정책 등) | 운송탭 UI |

`TransportOptions` 필드(초안):
- `include_cantilever: bool = True` — 캔틸 부재를 부모 모듈에 흡수할지(False) 별도 출하할지(True)
- `cantilever_packing_mode: str = 'embedded' | 'separate'`
- `nonbearing_wall_policy: str = 'auto_by_2d' | 'all_interior' | 'all_exterior' | 'manual'` — (C) 분석에서 확정
- `interior_wall_unit_weight: float = 30.0` (kg/m²)
- `exterior_wall_unit_weight: float = 55.0`
- `floor_slab_thickness_mm: float = 150.0` (geometry 통일값 기본)
- `concrete_density_kg_m3: float = 2400.0`
- `slab_rebar_ratio: float = 0.012`
- `treat_v3_module_as_lying: bool = True` — Vertical3Module 눕히기 자동 적용
- `mid_member_inclusion: str = 'extra_weight' | 'ignore'` — MidBeam/MidColumn 처리

### 2. 출력 계약

```
@dataclass
class TransportInput:
    modules: List[transport.models.Module]
    panels:  List[transport.models.Panel]     # floor / wall / lshape / lshape2 / lshape3
    excluded: List[ExcludedItem]               # 운송 대상 외(코어 등) — 로그·검증용
    diagnostics: Diagnostics                   # 변환 중 경고·정보
    source_index: Dict[str, List[int]]         # 운송 item.name → 우리 컴포넌트 cid 역인덱스
```

- `excluded`: Core/CoreSlab/RC 부재. 디버깅용. 운송 packer는 안 봄.
- `diagnostics.warnings`: "모듈 #7 의 4 기둥 단면이 서로 다름 — 가장 큰 단면 채택" 등.
- `source_index`: 운송 결과 표에서 사용자가 한 행을 클릭하면 우리 3D 씬 하이라이트가 가능하도록 역방향 추적용.

            # 처리된 wall들은 set에 기록해 나중에 독립 wall 분기에서 스킵
            processed_walls.update(comp.merged_wall_ids)
        else:
            panels.append(convert_floor_panel(comp, ...))
    elif isinstance(comp, StructWall):
        if cid in processed_walls or comp.merged_fp_id is not None:
            continue   # 이미 dependent로 처리됨
        panels.append(convert_independent_wall(comp, ...))
    elif isinstance(comp, (CantileverBeam, CantileverSlab)):
        if options.include_cantilever == 'separate':
            panels.append(convert_cantilever(...))
        # 'embedded'면 무시 (부모 모듈 extra_weight에 가산 — 별도 헬퍼 필요)
    elif isinstance(comp, (MidBeam, MidColumn)):
        continue  # 부모 모듈 extra_weight에 이미 가산됨 (compute_extra_weight_module 내부)
```

### 5. 단면 룩업 규약 — `lookup_section`

층구간 분할 결과 그룹명 규약 (`columns`, `columns_F1_3`, `columns_F4`, `beams`, `cantilevers`, `all_steel`):
1. `design_result.member_to_group.get(mid)` → 그룹명 획득
2. 그룹명에 `_F` 접미가 있으면 분할 그룹 — 호출자는 mid가 해당 층 범위에 속하는지 이미 보장됨(design 단계에서 분할)
3. `design_result.groups[gname].section` → SHSSection 반환
4. `mid` 가 어떤 그룹에도 안 속하면(RC 코어 등) `None` 반환 — 운송 변환에서 제외 처리

**일관성 검증** (`convert_module` 내부):
- 모듈 4 기둥 mid 의 lookup_section 결과가 모두 같은지 확인. 다르면 가장 무거운 단면 채택 + diagnostics.warning. (정상 케이스는 같은 모듈 내 4 기둥이 모두 같은 층 그룹에 속함)
- 모듈 8 보 mid 의 lookup_section 결과도 동일 검사.

### 6. extra_weight 계산 — 이중계산 회피

```
def compute_extra_weight_module(comp, options) -> float:
    w_m = comp.dimensions['width'] / 1000
    l_m = comp.dimensions['depth'] / 1000
    h_m = comp.dimensions['height'] / 1000
    area = w_m * l_m

    # 슬래브 자중
    slab_kg = area * (options.floor_slab_thickness_mm / 1000) * options.concrete_density_kg_m3

    # 비내력벽 4면 — options.nonbearing_wall_policy에 따라 면별 단위중량 결정
    wall_kg = sum_of_4_face_weights(comp, options)

    # MidBeam/MidColumn 강재 자중 (모듈 내부 보강재)
    mid_kg = sum_steel_weight_of_mid_members(comp, options)

    # ※ 4 기둥 + 8 보(천장·바닥 둘레)는 운송 측 Module.weight property에서 자동 계산되므로
    #    여기서는 가산하지 않는다. (B-11 수정 후 정답 일치 보장)

    return slab_kg + wall_kg + mid_kg
```

### 4. 핵심 메서드 시그니처

```
class TransportTabMixin:
    # 시그널
    transport_member_highlight = pyqtSignal(list)
    transport_blocked = pyqtSignal(int)

    def _build_transport_tab(self):
        page = QWidget()
        layout = QVBoxLayout(page)
        # ①~⑧ 위젯 빌드 …
        self._tabs.addTab(page, "운송")
        self._transport_tab_index = self._tabs.count() - 1

    def _on_policy_sync(self, policy: str): ...
    def _on_seg_sync(self, n: int): ...
    def _on_scene_modified(self): ...
    def _on_design_completed(self, design_result: dict): ...

    def _run_transport(self):
        """현재 옵션·정책으로 어댑터 + 패커 실행 → 결과 렌더링."""
        if not self._design_result_cache:
            self._show_error("구조해석을 먼저 실행하세요")
            return
        options = self._read_transport_options()
        try:
            ti = build_transport_input(
                self._scene, self._design_result_cache,
                self._current_policy, options)
        except TransportError as e:
            self._show_error(str(e)); return
        trucks = self._load_trucks()
        road = self._selected_road()
        spacing = self._read_spacing()
        result = pack_items(ti.modules, ti.panels, trucks, road, spacing)
        self._render_transport_result(ti, result)
        self._render_diagnostics(ti.diagnostics)

    def _render_transport_result(self, ti, pack_result):
        self._update_metrics(pack_result)
        self._update_trip_table(pack_result)
        self._update_util_chart(pack_result)
        self._update_view_combo(pack_result)
        self._update_economics(pack_result)
        self._update_override_table(pack_result)
        self._source_index = ti.source_index

    def _render_views(self, trip_no: int):
        trip = self._find_trip(trip_no)
        top_html = pio.to_html(draw_top_view(trip, trip.truck, sp), include_plotlyjs='cdn', full_html=True)
        rear_html = pio.to_html(draw_rear_view(trip, trip.truck, sp), include_plotlyjs='cdn', full_html=True)
        self._top_view_web.setHtml(top_html)
        self._rear_view_web.setHtml(rear_html)

    def _on_trip_row_double_clicked(self, row, col):
        trip_no = int(self._trip_table.item(row, 0).text())
        trip = self._find_trip(trip_no)
        cids = []
        for item in trip.items:
            cids.extend(self._source_index.get(item.name, []))
        self.transport_member_highlight.emit(cids)
```

### 8. 상태 머신

```
state ∈ {NoDesign, Ready, Computing, ResultShown, Error}

NoDesign       — 구조해석 미실행. 옵션·실행 버튼 비활성
Ready          — design_result 있음, 아직 실행 안 함. 실행 버튼 활성
Computing      — _run_transport 실행 중. 옵션 잠금
ResultShown    — 결과 표시 중. 옵션 변경 시 자동재계산 또는 수동 재실행

```

상태 전이는 `Controller` 의 `set_state()` 패턴 따라 단일 슬롯에서 위젯 enable/disable.

## 분석 ⑥ — 비내력벽 외부/내부 자동 판별 알고리즘 (C)

### 0. 문제 정의

모듈 1개에는 4 면의 비내력벽이 있고, 각 면은 **내부 비내력벽(30 kg/m²)** 또는 **외부 비내력벽(55 kg/m²)** 둘 중 하나로 분류돼야 함. 분류 기준:
- 그 면이 건물 외부 공기에 노출되면 외부
- 그 면이 다른 모듈·패널과 마주 보면 내부

수동 입력은 모듈 N개 × 4면 = N·4 회 클릭 → 사용자 부담. **자동 판별 필요**.

### 1. 사용자 제안 알고리즘 (채택안) — 20mm 오프셋 인접성 검사 + 비율

#### 원리

우리 배치 정책: **부재 사이 20mm 갭** (`feedback_snap_policy`, `JOINT_HORIZ_CONNECT_MAX_MM`). 즉 모듈 A의 면과 인접 모듈 B의 면 사이는 정확히 20mm 떨어짐.

판별 절차:
1. 모듈의 한 면을 사방으로 **20mm + ε(예 5mm) 만큼 오프셋 확장** → 확장된 면 영역 박스(slab) 생성
2. 그 박스가 **다른 부재(다른 모듈·플로어패널·구조벽 등)와 교차(intersect)** 하는지 검사
3. 교차하는 길이/면적 비율 계산 → **비율 ≥ θ 이면 내부, 아니면 외부**

#### 비율 계산 (사용자 아이디어 핵심)

면 한 변이 전부 다른 모듈과 맞닿는 경우는 드묾. 모듈 길이 일부만 인접하고 일부는 외부에 노출되는 케이스가 일반적 (예: 6m 모듈 중 4m만 옆 모듈과 붙고 2m는 외부).

→ 한 면을 **세그먼트 단위로 잘라** 각 세그먼트가 외부인지 내부인지 판정 → **외부 길이 / 전체 길이 비율** 산출.

- `비율 < 0.5` → 그 면은 **외부 비내력벽** (외부 노출이 우세)
- `비율 ≥ 0.5` → **내부 비내력벽**

단위중량 계산 시 더 정밀하게는 `unit_weight = 비율 × 외부단위중량 + (1-비율) × 내부단위중량` (혼합). 사용자 의견 "약간 오차 OK"이므로 임계값 분류로 시작, 옵션으로 혼합 모드 토글.

#### 의사 코드

```
def classify_module_face(module, face_name, scene, gap_mm=20.0, eps_mm=5.0):
    """
    face_name ∈ {"전면","후면","좌면","우면"}
    Returns: (classification: "interior"|"exterior", exterior_ratio: float)
    """
    # 1. 면 평면 + 두 면내 축벡터 얻기
    plane_origin, plane_normal, u_axis, v_axis, u_len, v_len = face_geometry(module, face_name)

    # 2. 사방으로 오프셋 확장한 박스(slab) 생성
    #    면 평면에서 외측으로 (gap + eps) 깊이의 얇은 박스
    probe_box = make_probe_slab(
        origin=plane_origin + plane_normal * (1.0),   # 면 바깥쪽 1mm부터
        u_axis=u_axis, v_axis=v_axis,
        u_len=u_len, v_len=v_len,
        depth=gap_mm + eps_mm,
    )

    # 3. u 방향을 N 세그먼트로 잘라 각 세그먼트 박스의 교차 검사
    N = max(int(u_len / 100), 10)   # 100mm 격자, 최소 10 세그먼트
    seg_u = u_len / N
    interior_len = 0.0
    for i in range(N):
        seg_box = sub_slab(probe_box, u_start=i*seg_u, u_end=(i+1)*seg_u)
        if any_intersect_with_other_components(seg_box, scene, exclude=[module.id]):
            interior_len += seg_u
    exterior_len = u_len - interior_len
    exterior_ratio = exterior_len / u_len

    classification = "exterior" if exterior_ratio >= 0.5 else "interior"
    return classification, exterior_ratio
```

#### 장점
- **명확하고 결정론적** — 같은 씬이면 항상 같은 결과
- **20mm 갭 정책에 자연스럽게 부합** — 우리 도메인 관행 그대로 활용
- **부분 인접 케이스 정밀 처리** — 비율 산출로 회색 영역 표현 가능
- **2D 평면도 분석으로 환원** — Z축 무시 가능(같은 층 모듈끼리만 비교), 계산 가벼움
- **혼합 단위중량 옵션** 가능 — 50/50 부분 인접 면을 평균 단위중량으로 계산하면 더 정확
- **다른 부재 종류 확장 용이** — Module ↔ Module 뿐 아니라 Module ↔ FloorPanel ↔ StructWall 모두 동일 인접 검사

#### 단점·한계
- **얇은 외피·발코니 등 변칙 케이스** 처리 모호 — 발코니 슬래브가 모듈 면 일부만 가리면? → 옵션으로 "FloorPanel은 인접 검사에서 제외" 토글 추가
- **두 모듈 사이에 통로/복도(공기층)**가 있는 케이스 — 통로 폭이 20mm보다 크면 자동 외부 판정. 실제로는 내부 공용 공간 → 사용자 수동 보정 필요. 사용자 명시 "약간의 오차 OK" 이므로 수용
- **격자 해상도 100mm** — 너무 작은 인접(예 90mm 외팔보 노출)은 놓침. 옵션으로 격자 크기 조절

### 2. 대안 알고리즘 비교

#### (B) Convex Hull 외곽 판정

평면(XY)에서 모든 모듈의 바닥 폴리곤 합집합 → 외곽선(convex hull 또는 alpha shape) 추출 → 모듈 면이 외곽선의 일부와 겹치면 외부.

- 장점: 한 번 계산으로 전체 외피 식별
- 단점: 凹(오목) 평면에서 convex hull은 부정확. Alpha shape은 매개변수 튜닝 필요. 통로/안마당 케이스 부정확

#### (C) Raycasting

각 면 중심에서 외측 방향으로 ray 발사 → 일정 거리(예 1m) 내 다른 부재 만나면 내부, 아니면 외부.

- 장점: 구현 단순
- 단점: 한 점만 보므로 면 일부 인접 케이스 누락. 비율 산출 어려움 (다중 ray로 보완 가능 — 결국 (A)와 유사)

#### 비교 표

| 항목 | (A) 20mm 오프셋 + 비율 | (B) Convex Hull | (C) Raycasting |
|---|---|---|---|
| 정확도 (균등 배치) | ★★★ | ★★ | ★★ |
| 부분 인접 처리 | ★★★ (비율 산출) | ★ | ★ (다중 ray 시 ★★) |
| 凹 평면 처리 | ★★★ | ★ | ★★★ |
| 통로/안마당 | ★★ (수동 보정) | ★ | ★★ |
| 구현 복잡도 | 중 | 중 | 하 |
| 도메인 적합성 | ★★★ (20mm 정책 활용) | ★ | ★★ |
| 확장성 (벽패널 등) | ★★★ | ★ | ★★ |

→ **(A) 채택**. (C)는 빠른 첫 구현용 fallback으로 보관.

def sum_of_4_face_weights(comp, options, classifier_result):
    face_areas = {
        "전면": (comp.dim.width/1000) * (comp.dim.height/1000),
        "후면": (comp.dim.width/1000) * (comp.dim.height/1000),
        "좌면": (comp.dim.depth/1000) * (comp.dim.height/1000),
        "우면": (comp.dim.depth/1000) * (comp.dim.height/1000),
    }
    cls = classifier_result.get(comp.id, {})
    total = 0.0
    for face_name, area in face_areas.items():
        fc = cls.get(face_name)
        if fc is None:
            unit = options.interior_wall_unit_weight  # 기본 내부
        else:
            unit = fc.unit_weight_kgm2
        total += unit * area
    return total
```

### 5. 성능·캐시

- 100 모듈 × 4면 × 20 세그먼트 = 8,000 인접 검사. AABB 박스 교차는 O(1). 모듈 수 N에 대해 검사 후보를 spatial hash(격자) 로 추리면 전체 O(N·log N) 수준.
- 씬 변경 없이 옵션만 바꿀 때 캐시 재사용 — `scene.fingerprint()` 키로 결과 저장 (분석 ⑧ 캐시 정책에서 통합).

### 6. 단위 테스트 시나리오

1. 단일 모듈 → 4 면 전부 exterior, ratio=1
2. 2개 모듈 좌우 인접 → 마주 보는 1 면씩 interior, 나머지 6 면 exterior
3. 2×2 그리드 4 모듈 → 각 모듈의 2 면 interior, 2 면 exterior
4. 부분 인접 (1개는 6m, 1개는 3m, 한 끝만 맞춤) → 6m 모듈의 한 면 ratio≈0.5
5. 통로 50mm 간격 (20mm 정책 위반) → 모두 exterior (외부 판정)
6. 발코니 FloorPanel 부착 + 옵션 토글 ON/OFF → 결과 다름
7. 凹 평면 (ㄴ자 배치) → 내측 모서리 면 interior, 외측 면 exterior

### 7. 사용자 결정 사항 (2026-05-19 확정)

1. **임계값 제거 · 비율 자체를 가중치로** — 모든 면을 외부/내부로 분류하지 않고, 외부 노출 비율을 그대로 가중치로 사용해 단위중량을 가중평균. 임계값 옵션·"분류 라벨" 자체 폐기.
2. **혼합 모드 항상 ON** — 사실상 1번과 동일. 옵션 토글이 아니라 기본 동작.
3. **FloorPanel을 인접 장애물로 포함** — 발코니·플로어패널이 모듈 면을 가리면 그 부분은 외부 노출에서 제외(즉 가중치 외부 비율 감소).

## 분석 ⑦ — 수동 시뮬레이션 모드 정의 (D)

def simulate_manual_trip(items, truck, road, spacing) -> (ok, reason, trip)
```

사용자가 직접 고른 화물 리스트 + 트럭 1대 + 도로 1종을 받아 **단일 회차** 가 가능한지만 판정 (자동 packing 전체 흐름과 분리). 가능하면 Trip 객체, 불가하면 사유 문자열 반환. 자동 결과와 독립.

### 2. 왜 필요한가 — 5 가지 쓰임새

1. **가설 검증** — "임시로 30 t 트럭을 빌릴 수 있다면 회차가 얼마나 줄지?" 카탈로그에 없는 트럭 치수·중량을 직접 입력해 1회차 시도
2. **신규 모듈 사전 검토** — 발주 전 단계, 아직 씬에 없는 모듈 사양(2.8×6×3 m, 8 t)을 임시로 만들어 어떤 트럭에 실리는지 확인
3. **부분 운송 가능성 확인** — "이 모듈 5 개를 한 회차에 실을 수 있을까?" 패킹 알고리즘이 다른 회차에 분산한 화물을 한 회차로 묶어 검증
4. **적재 한계 탐색** — 임의 트럭·도로 조합의 최대 적재 수량을 사용자가 수동으로 탐색
5. **자동 결과 디버깅** — 자동 패킹이 어떤 화물을 NG로 뱉었을 때, 트럭/도로만 바꿔서 어디까지 풀리는지 즉시 확인

→ "**자동 결과 표는 만들어진 회차의 검증**, **수동 시뮬레이션은 미래·가설·임시 화물의 검증**" 으로 역할 분리.

### 3. 회차별 override 기능과의 차이

| 항목 | 회차별 트럭 override | 수동 시뮬레이션 |
|---|---|---|
| 대상 화물 | 자동 결과의 실재 회차 | 사용자가 임의 구성 |
| 트럭 | 카탈로그 |  카탈로그 + 커스텀 |
| 결과 | 자동 결과 갱신 (반영) | 별도 표시 (반영 안 함) |
| 도로 | 자동과 공유 | 별도 선택 가능 |
| 간격 | 자동과 공유 | 별도 선택 가능 |

→ override는 "**미세 조정**", 수동 시뮬레이션은 "**탐색·가설**".

### 5. 동작 흐름 (시나리오별)

### 6. 어댑터·패커와의 인터페이스

```
# modular_3d/transport/manual_sim.py (신규)

@dataclass
class ManualSimInput:
    items: List[Module|Panel]   # 운송 객체 (어댑터 결과 또는 임시 빌드)
    truck: Truck
    road: RoadClass
    spacing: SpacingParams

@dataclass
class ManualSimResult:
    ok: bool
    reason: str
    trip: Optional[Trip]
    cargo_weight: float
    weight_utilization: float
    length_utilization: float

def run_manual_sim(input: ManualSimInput) -> ManualSimResult:
    ok, reason, trip = simulate_manual_trip(
        input.items, input.truck, input.road, input.spacing)
    if not ok or trip is None:
        return ManualSimResult(ok=False, reason=reason, trip=None,
                                cargo_weight=0, weight_utilization=0,
                                length_utilization=0)
    return ManualSimResult(
        ok=True, reason="OK", trip=trip,
        cargo_weight=trip.cargo_weight,
        weight_utilization=trip.weight_utilization,
        length_utilization=trip.length_utilization)
```

`simulate_manual_trip` 자체는 운송프로그램 원본을 그대로 가져옴(분석 ③에서 🟢필수 격상). B-시리즈 버그 수정 적용 필요.

### 7. 헷갈리기 쉬운 케이스 (구현 시 주의)

- **임시 모듈의 단면이 우리 SHS_CATALOG에 없는 형강(H·C·L)** 인 경우: 운송 측 Section 데이터모델은 SHS·RHS·H·C·L·CFT 모두 지원하므로 임시 화물 정의 모달에서 카탈로그 전체 노출. 우리 어댑터를 거치는 케이스(A·B)는 SHS만 가능.
- **임시 화물이 종속 패널(L자/ㄷ자/3면)** 인 경우: 임시 정의 모달이 복잡해짐. 1단계에서는 임시 모드에서 L자만 지원, ㄷ자·3면은 제외(또는 차후 확장).
- **여러 종류 패널 혼적**: `simulate_manual_trip` 원본은 같은 kind 패널만 허용(모듈+패널 섞기 X). 그대로 유지.
- **수직3모듈을 시뮬레이션**: 어댑터의 `convert_vertical3_lying` 으로 변환 후 시뮬레이션.

### 8. 결과 영역 — 도식 재사용

자동 결과의 `_render_views` (분석 ⑤ 4번 메서드) 를 동일하게 호출. trip 객체 형태가 같으므로 추가 코드 거의 없음.

### 9. 자동 결과로의 편입 (영역 ⑧, 옵션)

[▷ 자동 결과에 추가] 버튼 — 시뮬레이션 결과 trip을 정식 운송 계획에 추가. 사용 의도:
- 사용자가 시뮬레이션으로 "이 트럭+화물 조합이 좋다"는 결론을 얻으면 그것을 정식 회차로 등록
- 단, 그러려면 화물이 우리 씬 부재(cid)에 매핑돼야 정합성 유지 → **임시 화물 정의 모드에서 만든 화물은 편입 불가**. 씬 부재 선택·자동 결과 복제만 가능.

→ 1단계는 이 버튼 보류 (구현 미정), 2단계에서 사용자 요구 시 추가.

### 10. 단위 테스트 시나리오

1. 자동 결과 회차 1개 복제 → 같은 트럭으로 시뮬 → ✓
2. 자동 결과 복제 → 한 단계 작은 트럭으로 시뮬 → ❌ 사유
3. 씬에서 모듈 cid 2개 선택 → 25 t 트럭으로 시뮬 → ✓
4. 임시 모듈 정의 (5×10 m, 20 t) → 어떤 트럭도 NG → 사유 "도로 한도 초과"
5. 커스텀 트럭 (30 t) → 임시 모듈 → ✓
6. 같은 kind 아닌 패널 혼합 → ❌ "한 회차에 다른 종류 패널 섞을 수 없음"
7. 비어있는 items → ❌ "화물 비어있음"

### 11. 사용자 결정 대기 사항

1. **임시 화물 정의 모달의 입력 깊이** — 운송프로그램 원본 폼(`_module_form` 등) 전체를 가져올지, 치수·단면·수량만 가져오는 축약형으로 만들지
2. **커스텀 트럭의 영속성** — 1회용 / 세션 동안 유지 / `trucks.json` 영구 저장 (위 ③에서 체크박스로 3안 제시했지만 확인 필요)
3. **자동 결과에 추가 버튼** 의 필요성 — 1 단계 보류 제안. 수용?
4. **수동 시뮬레이션 결과 저장** — 시뮬한 결과들을 히스토리로 누적해서 비교 가능하게 할지

→ 분석 ⑧ 진행. (수동 시뮬레이션 사용자 결정 4건은 구현 진입 직전 시점에 일괄 결정 권장)

## 분석 ⑧ — 재계산·캐시 무효화 정책 (E)

운송탭 결과가 만들어지기까지 거치는 단계는 8개이고 각 단계가 비용·의존성이 다르므로 단계별 캐시·무효화 트리거를 명확히 정의해야 사용자가 옵션을 살짝 바꿔도 매번 구조해석을 다시 돌리는 비효율이 사라진다.

### 1. 파이프라인 8 단계

```
[1] 씬 편집 (3D GUI)
  ↓
[2] 구조해석 (OpenSeesPy) ────────  비용: 큼 (수 초~수십 초)
  ↓
[3] 단면 산정 (DesignResult, 정책별) ─  비용: 중 (수십~수백 ms)
  ↓
[4] 층구간 분할 (n_segments, DP)  ───  비용: 작음
  ↓
[5] 비내력벽 분류 (wall_classifier) ─  비용: 중 (씬 부재 수 N에 대해 O(N·log N))
  ↓
[6] 어댑터 변환 (build_transport_input) ─ 비용: 작음
  ↓
[7] 패킹 (pack_items) ─────────────  비용: 작음
  ↓
[8] 운임 계산 + 시각화 ───────────  비용: 매우 작음
```

### 2. 캐시 키 — 8 단계별

각 단계는 입력 해시(또는 fingerprint)를 캐시 키로 한다.

| 단계 | 캐시 키 | 입력 해시 구성 |
|---|---|---|
| [1] 씬 | `scene_fp` | 모든 컴포넌트의 (cid, type, dimensions, position, rotation, anchor, merged_*, role) 직렬화 → SHA-256 |
| [2] 해석 | `analysis_fp` | `scene_fp` + 해석 설정(케이스·하중) |
| [3] 단면 | `design_fp(policy)` | `analysis_fp` + policy + catalog version |
| [4] 분할 | `seg_fp(policy, n)` | `design_fp(policy)` + n_segments + 분할 알고리즘 ver |
| [5] 분류 | `classify_fp` | `scene_fp` + (gap_mm, eps_mm, segment_size_mm, include_floor_panels) |
| [6] 어댑터 | `ti_fp` | `seg_fp(policy,n)` + `classify_fp` + transport_options_hash |
| [7] 패킹 | `pack_fp` | `ti_fp` + trucks_fp + road + spacing |
| [8] 운임 | (즉시 계산) | `pack_fp` + (distance, speed, rate_extendable) |

`scene_fp` 는 우리 씬에 이미 fingerprint 메서드가 있는지 확인 필요(없으면 헬퍼 신규). 모든 하위 fp는 상위 fp + 추가 인자 해시.

### 3. 무효화 트리거 매트릭스

사용자 액션 → 어느 캐시부터 무효화되는지:

| 사용자 액션 | [2]해석 | [3]단면 | [4]분할 | [5]분류 | [6]어댑터 | [7]패킹 | [8]운임/그림 |
|---|---|---|---|---|---|---|---|
| 씬 부재 추가·삭제·이동·치수 변경 | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| 정책 라디오 변경 | ○ | ✗ | ✗ | ○ | ✗ | ✗ | ✗ |
| 층구간 n 변경 | ○ | ○ | ✗ | ○ | ✗ | ✗ | ✗ |
| 비내력벽 격자·옵션 변경 | ○ | ○ | ○ | ✗ | ✗ | ✗ | ✗ |
| 비내력벽 단위중량(30/55) 변경 | ○ | ○ | ○ | ○ | ✗ | ✗ | ✗ |

표 읽는 법:
- ○ = 캐시 유지 (재사용 가능)
- ✗ = 캐시 무효 → 그 단계부터 아래로 재계산

핵심 인사이트:
- **단위중량 30/55 변경은 [6] 어댑터부터만 재계산** — [5] 분류는 비율만 계산하므로 단위중량 변경은 무효화 안 함. 어댑터의 `face_unit_weight` 가중평균만 다시 돈다.

- **트럭 카탈로그 편집은 [7] 패킹부터** — 어댑터까지는 트럭과 무관
- **씬 편집은 전체 재계산** — 단 [2] 구조해석은 비싸므로 자동 트리거 X (아래 5번)

### 4. 자동 / 수동 재계산 모드

운송탭 옵션 영역에 **자동 재계산** 체크박스(기본 ON):

- **자동 ON**: 옵션·정책·간격 등 가벼운 입력 변경은 즉시 ([5]~[8]) 재계산. **씬 편집은 예외** — 사용자가 "구조해석 실행" 버튼을 다시 누를 때까지 [2] 무효화만 표시.
- **자동 OFF**: 모든 변경 시 캐시 무효 표시만 하고 [▷ 운송 계산 실행] 버튼 강조. 사용자가 명시 호출.

### 5. 비싼 단계의 보호 — [2] 구조해석

구조해석은 OpenSeesPy 실행이라 수 초~수십 초. 자동 재계산 대상에서 **항상 제외**.
- 씬 편집이 감지되면: 상태바에 "⚠ 씬이 변경됨 → 구조해석 다시 필요" 표시 + [▷ 구조해석 실행] 버튼 활성
- 사용자가 명시 실행 → [2] 갱신 + [3]~[8] 자동 chain

이미 우리 분석탭이 같은 패턴 (사용자가 "해석 실행" 명시 호출).

### 6. 상태 표시 — 상태바 (분석 ⑤ 영역 ①)

운송탭 상단 상태바에 8 단계 상태 인디케이터:

```
[해석 ✓] [단면 ✓] [분할 ✓] [분류 ✓] [변환 ✓] [패킹 ✗] [운임 ✗] [그림 ✗]
```

- ✓ 캐시 hit (재사용 가능)
- ✗ stale (재계산 필요)
- 회색 = 미실행
- 빨강 = 입력 일관성 깨짐 (예: 정책이 design_result 키에 없음)

상태바 한 줄로 "지금 클릭하면 어디까지 다시 돌지" 사용자가 즉시 파악.

### 7. 구현 모델 — Lazy Memoization

```

### 8. 동시성·중복 호출 방지

자동 재계산 모드에서 사용자가 옵션을 빠르게 여러 번 바꾸면 같은 계산이 여러 번 트리거될 위험. 대응:

- **디바운스**: 옵션 위젯의 `valueChanged` 시그널을 200~500 ms 디바운스 후 단 1회 `_run_transport()` 호출
- **계산 중 중복 차단**: `state == Computing` 동안 위젯 잠금 (분석 ⑤ 8번 상태 머신과 연동)
- **백그라운드 스레드(선택)**: [5] 분류·[7] 패킹이 큰 씬에서 100 ms 넘으면 QThread로 백그라운드 실행 — 1단계는 동기 호출, 2단계에서 도입

### 9. 외부 시그널과의 연동

기존 구조해석탭·물량탭에서 발신해야 할 신규 시그널:

| 발신 위젯 | 시그널 | 무효화 대상 |
|---|---|---|
| AnalysisPanel | `analysis_completed(scene_fp, ops_results)` | [2] 캐시 채움, [3]~[8] 무효화 |
| AnalysisPanel | `policy_changed(str)` | [3] 단면 재산정 트리거 (정책별 캐시 hit이면 즉시 사용) |
| AnalysisPanel | `column_segments_changed(int)` | [4] 분할 재계산 |
| Controller | `scene_modified()` | [2]~[8] 무효화 (해석 결과 표시는 stale 마크) |

기존 `column_segments_changed` 는 이미 존재. `policy_changed` 와 `analysis_completed` 는 신규 시그널 추가 필요.

### 10. 단위 테스트 시나리오

1. 첫 호출 → 전부 miss → 8단계 모두 계산
2. 같은 입력 재호출 → 전부 hit → 0 추가 계산
3. 단위중량만 변경 → [6] 어댑터부터 재계산, [5] 분류 hit 확인
4. 정책 변경 후 다시 원래 정책 복귀 → design_results 캐시 hit (dict 보관)
5. 씬 편집 → [2] stale 표시만, 자동 재계산 안 함
6. 사용자가 명시 [▷구조해석 실행] → 전체 chain 재계산
7. 두 위젯 동시 변경 (디바운스 검증) → 마지막 값으로 1회만 계산

### 11. 사용자 결정 대기 사항

1. **자동 재계산 기본 ON/OFF** — ON 제안 (씬 편집만 예외). 수용?
2. **디바운스 시간** — 200 ms / 500 ms / 1000 ms 중. 200 ms 제안 (반응성 우선)
3. **상태바 인디케이터 노출 여부** — 8 단계 모두 표시 vs 요약 1줄 ("재계산 필요 ✗" 또는 "최신 ✓"). 8 단계 표시는 디버깅엔 좋지만 초보 사용자엔 부담
4. **정책별 design_results 캐시 보관 개수** — 3 정책 모두 보관(메모리 약간 늘지만 즉시 전환) vs 마지막 1개만 보관. 3개 보관 제안

def validate_truck(t: dict) -> List[str]:
    errors = []
    if t["truck_type"] not in ("lowbed", "extendable", "aframe"):
        errors.append(f"truck_type 오타: {t['truck_type']}")
    for f in ("max_length", "max_width", "max_height", "max_weight",
              "vehicle_height_offset", "curb_weight_kg", "trailer_length_mm"):
        if t.get(f, 0) < 0:
            errors.append(f"{f} 음수 불가")
    if t["max_height"] <= t["vehicle_height_offset"]:
        errors.append("max_height ≤ vehicle_height_offset — 적재 공간 0")
    if t["hourly_rate_krw"] < 0:
        errors.append("시간단가 음수 불가")
    # 권장(경고)
    if t["curb_weight_kg"] == 0:
        warnings.append("차량중량 0 — 도로 GVW 검사가 부정확할 수 있음")
    if t["trailer_length_mm"] == 0:
        warnings.append("트레일러길이 0 — 도로 길이 검사가 부정확할 수 있음")
    return errors

4. 잘못된 truck_type 추가 → 검증 실패, 저장 안 됨
5. 내장 트럭 [편집] 시도 → "복제 후 편집" 안내 다이얼로그
6. 프로젝트 트럭 정의 후 다른 프로젝트 열기 → 표시 안 됨
7. 사용자 트럭 삭제 → 다음 로드 시 사라짐

### 12. 사용자 결정 대기 사항

1. **사용자 디렉토리 경로** — `~/.modular_3d/transport/` 제안. macOS/Windows 모두 동일 경로. 수용?
2. **프로젝트 임시 카탈로그 지원 여부** — 1단계는 [1]+[2] 만 구현, [3] 프로젝트는 2단계 보류 제안
3. **차량중량·트레일러길이 디폴트값** — 위 6번의 추정치 사용 OK? 아니면 실제 값을 직접 채워주실 수 있는지
4. **편집 권한 UX** — clone-on-edit 다이얼로그 vs 직접 잠금(편집 불가 메시지) 중 선호
5. **카탈로그 표를 운송탭 안 vs 별도 [환경설정] 다이얼로그** — 운송탭 영역 ⑤로 통합 제안 (분석 ⑤ 그대로)

→ 분석 ⑨ 까지 완료. 6개 자율 분석 마침.
