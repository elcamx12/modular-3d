# 물량탭 대대적 개편 계획서

작성일: 2026-05-31
대상: `modular_3d` — 물량(Quantity) 탭의 좌측 3D + 우측 패널 전면 교체

---

## §0. 목표 한 줄 요약

물량탭 좌측의 **와이어프레임을 제거**하고, **운송 3D 시각화 파이프라인을 재사용**해
각 단면설계 타입의 컴포넌트(모듈/패널, 종속부재 포함)를 트럭 없이 바닥에 평면 배치한다.
우측 패널은 부재별 응력비 트리를 **타입별 물량·비용 트리**로 개조하고,
그 아래에 기존 강재 본수표·자재비표(프로젝트 전체 기준)를 살린다.

## §1. 사용자 확정 사항 (질문·답변 종합)

### 1-1. 레이아웃
- 좌측 와이어프레임 → **운송식 Three.js 3D 뷰어**로 교체. 트럭 박스는 그리지 않음.
- 3D 화면 **내부**에 텍스트 라벨(타입명 + 층 정보 + 부재별 단면 목록)을 넣는다.
  운송의 그룹 라벨(CSS2DObject)과 동일 방식. 타입목록과 텍스트는 한 덩어리.
- 우측 패널 = 비용 패널(타입별 물량·금액 트리 + 하단 본수표·자재비표).
- 기존 5개 표(채택단면표·강재본수표·슬래브표·자재비표·응력비트리)는 **전부 제거** 후
  새 구조로 대체. 단, **강재 본수표·자재비표는 우측 트리 아래에 살려서 재배치**.

### 1-2. 3D 시각화 동작
- 트럭 없음 → 모든 컴포넌트를 **바닥(z=0) 평면 배치**, 적층 없음(축적 적재 X).
- **같은 타입** 여러 개: 운송에서 "같은 회차를 폭방향으로 겹쳐 누적"하던 것과
  **동일 간격**으로 트럭 진행방향 기준 오른쪽(= Python -Y, 운송 `INTRA_GROUP_GAP_M`)에 일렬.
  → **줄바꿈 없음** (사용자 정정: 같은 타입은 줄바꿈 기준 자체가 없음).
- **다른 타입**: 진행방향 뒤(= Python +X)로 분리. 간격은 **종속부재 포함 외곽 끝과 끝이 3m**.
  (운송 `INTER_TRUCK_GAP_M`=4.0 이 아니라 **3.0m**, 그리고 트럭 길이가 아닌 *실제 외곽 길이* 기준)
- 같은 타입 80개면 **80개 전부** 그린다.
- 진입 시 **모든 타입 한 번에** 표시.

### 1-3. 표시 대상
- 모듈 / 바닥패널 / 벽패널 = 전부 표시. **RC 코어는 제외**.
- 종속부재(캔틸레버보·슬래브, 중간보·중간기둥, 벽 세그먼트) 디테일 모두 표시.
  → 단면설계 우측 패널 3D에서 그리던 부재 단위 렌더를 그대로 사용(= 운송 어댑터 body_parts).

### 1-4. 중간 텍스트 (3D 내부 라벨)
- 타입당 1회 (같은 타입은 동일하므로). 양식: `타입명 (N층 ...)` + 그 아래
  `기둥 SHS250×250×8 / 천장보 ... / 바닥보 ...` 부재별 단면 목록.
- **응력비 괄호값 제외** — 단면명만 표시.

### 1-5. 우측 비용 패널
- 부재별 응력비 트리를 개조 → **[타입] > [역할(기둥/천장보/바닥보 등)] > [부재]** 계층.
  (현재는 [타입]>[N층]>[역할]>[부재] 4단 — 층 단계는 타입이 이미 단면을 구분하므로 통합 검토)
- 트리를 펼치면 각 항목의 **물량 + 금액** 표시. 상위 노드 값은 **숨기고** 세부 항목만 보여줌.
- 개별 금액 + 상위 트리 합산 금액(합산은 숨김 처리하되 최종 총합은 별도 표기).
- 데크슬래브·콘크리트 비용은 **컴포넌트 소속 슬래브 기준**으로 타입에 귀속.
- 트리 아래 강재 본수표·자재비표는 **항상 프로젝트 전체** 기준.

### 1-6. 기준 결과 / 정책
- 정책 라디오(1·2·3종), 기둥 층구간 입력 등 **모든 인풋 위젯 제거**.
- 표시 기준 = **단면설계 탭의 현재 채택 결과**.
- 단면이 다르면 단면설계가 이미 **다른 타입**으로 분류 → 타입별 개수·층별 개수(`floor_counts`) 보유.

### 1-8. (2026-05-31 추가 확정)
- **층 단계 통합**: 같은 타입이 여러 층에 걸쳐도 트리에서 층을 따로 보지 않는다.
  물량만 뽑는 화면이므로 층 구분 불필요 → 트리 계층은 **[타입] > [역할] > [부재]** (층 단계 없음).
  (단면이 층마다 다르면 그건 애초에 다른 타입으로 갈라져 있으므로 정보 손실 없음.)
- **트럭/적재공간 완전 제거**: 트럭 차체(캐빈·바퀴·프레임)와 적재함 외곽선·바닥판
  **모두 그리지 않는다**. 화물(부재)만 바닥에 배치.

### 1-7. 편의 기능 (3D)
- 트리 ↔ 3D **양방향 강조**, 마우스 회전·줌·이동(OrbitControls), 호버 툴팁.
- 적층 가능성 고려 안 함(평면 배치만).

    되고, 평가탭이 쓰는 그 dict 를 *공유*(별도 사본 만들지 말 것).

## §3. 신규/변경 컴포넌트 설계

### 3-A. 컴포넌트별 물량 분해기 (신규) — `analysis/quantity_by_component.py`
**목적**: 각 컴포넌트(cid)의 강재(역할별 단면·본수·중량·금액) + 데크면적 + 콘크리트부피 + 금액.

데이터 자료형(초안):
- `ComponentSteelLine`: role_ko, section_name, section_type, count, total_length_m, total_weight_ton, cost
- `ComponentQuantity`: cid, label, type_label, floor, steel_lines[], deck_area_m2, deck_cost,
  concrete_m3, concrete_cost, steel_cost, total_cost
- `TypeQuantity`: type_label, instance_count, member_cids[], rep ComponentQuantity,
  type_total_cost(=인스턴스 합), per-instance cost

계산 흐름:
1. `model.comp_to_members[cid]` 순회 → 부재별 단면(`lookup_section_for_member`) + 길이 + 역할(`_classify_role_ko` 재사용).
2. 역할별·단면별 묶음 → 본수/중량/금액(강재 단가 × 중량).
3. 슬래브: 컴포넌트 소속 슬래브 → 면적·부피 → 데크·콘크리트 금액.
4. 타입으로 그룹핑(cid 기준, 라벨 문자열 아님). 합산은 comp_ids 전체 실측.

⚠ **슬래브 귀속 — 캔틸 슬래브 누락 위험(중대)**:
- 슬래브를 가진 컴포넌트 종류: 모듈(`.slabs` 리스트), FloorPanel(`.slab`), CantileverSlab(`.slab`),
  CoreSlab(`.slab`). 전체 합산기 `aggregate_slabs._collect_slabs` 는 **CoreSlab 만 제외**하고
  나머지(모듈·FloorPanel·**CantileverSlab**)는 전부 전체 합에 포함한다.
- 그런데 **CantileverSlab 은 별도 컴포넌트**(sub_index>0, parent_id=부모)라 타입 목록(독립부재)에
  안 나온다. 컴포넌트별로 모듈/패널의 `.slabs`/`.slab` 만 모으면 **캔틸 슬래브가 누락** →
  "Σ(컴포넌트 슬래브) < 전체 슬래브" → Phase 1 검증 실패.
- **대응**: 컴포넌트별 슬래브 집계 시 그 컴포넌트의 **본체 슬래브 + parent_id 가 자신인 CantileverSlab
  의 슬래브**를 함께 귀속한다(아래 "타입에 없는 cid 전부 부모 귀속" 규칙의 슬래브판 — 동일 귀속맵).
  코어 슬래브는 양쪽 모두 제외(일관).
- 검증: Σ(타입별 comp_ids 슬래브) == `aggregate_slabs(scene)` 전체값.
- **혼동 주의**: 어댑터 `extra_weight`(캔틸 강재 자중을 부모에 합산)는 *운송 무게*용 경로이고, 물량
  탭의 강재 ton·비용은 *별개 경로*(comp_to_members mid → 단면 → 중량). 두 경로를 섞지 말 것.

**재사용**: `aggregate_steel`의 parent_root 묶음 로직, `compute_material_cost` 단가 적용 방식,
`_classify_role_ko`(analysis_panel → 공용 위치로 추출), `lookup_section_for_member`(adapter),
캔틸 귀속은 `_sum_cantilever_weight_attached_to` 의 parent_id 매칭 패턴.

⚠ **"타입에 없는 cid" 전부 부모 귀속 — 검증식의 핵심 조건(중대)**:
- `aggregate_steel`(전체)은 **모든 cid 의 부재**(캔틸 beam, Mid beam/column, 흡수벽 포함)를 합산한다
  (캔틸·Mid 도 `comp_to_members[cid]` 에 mid 보유 — topology L1010, member_to_group 에 잡힘).
- 타입 목록(`derive_section_types`)은 **독립부재 본체만**(`_is_indep_steel_comp`: MODULE/FLOOR_PANEL/
  STRUCT_WALL(흡수 아닌)/VERTICAL_MODULE, sub_index==0). → 캔틸·Mid·흡수벽은 타입에 **없음**.
- 따라서 타입별 cid 만 순회하면 **그 차집합(캔틸·Mid·흡수벽)의 강재가 통째로 누락** → "Σ타입 < 전체".
- **대응(정확한 방법)**: 캔틸·Mid·흡수벽의 강재는 *시각화 박스(attached_parts)에서 역산 금지*. 반드시
  그 cid 의 `comp_to_members[cid]` mid 를 직접 합산해 **부모 cid(parent_id 또는 merged_fp_id)**의
  타입 물량에 더한다. 그리고 그 cid 는 독립 순회에서 제외(이중계산 방지).
- **귀속 맵 구성**: `child_to_parent = {캔틸/Mid cid: parent_id, 흡수벽 cid: merged_fp_id}`.
  부모가 또 타입에 없으면(예외) 경고 + 미귀속 집계로 남겨 검증에서 드러나게.
- **검증식**: Σ(타입별 모든 귀속 cid 의 강재 ton) == `aggregate_steel` 전체 ton (round 오차 내).
  슬래브·콘크리트도 동일: Σ(타입 귀속 슬래브) == `aggregate_slabs` 전체.

✅ **단가 조회 안전 확인**: `material_prices.json` 키 4종(`강재_각형강관_SHS`, `강재_H형강`,
`콘크리트_레미콘`, `데크슬래브`) 모두 존재. 강재 단가는 강종 무관 ton 단가라, 컴포넌트별도 기존
`compute_material_cost` 와 같은 방식(ton×단가)으로 곱하면 전체와 일치. (단, H형강 단가는 "현재
미사용" 주석 — 각형강관만 산출되는 모델 가정. H형강 섞이면 강종 분리 합산 유지.)

⚠ **강재 본수 round 묶음의 컴포넌트 분해 주의**: `aggregate_steel` 은 (단면, round길이) 버킷으로 본수를
묶는다(LENGTH_ROUND_MM=1mm). 컴포넌트별로 쪼개면 같은 버킷이 여러 컴포넌트에 흩어진다. 본수·중량은
컴포넌트 내에서 다시 묶어 표시하되, **전체 본수표(하단, 프로젝트 전체)는 기존 `aggregate_steel` 결과를
그대로** 쓴다(재계산 금지 — round 누적 차이로 합계 어긋남 방지).

### 3-B. 물량탭용 3D 데이터 빌더 (신규) — `transport/loaded_3d_three.py` 에 추가
**목적**: 트럭 없이 타입별 인스턴스를 평면 배치한 Three.js JSON + HTML 생성.

신규 함수(운송 함수와 분리, 회귀 위험 차단):
- `serialize_quantity_for_three(items_by_type, ...)` — `serialize_pack_for_three` 의 물량탭판.
  - 입력: 타입(**cid 집합으로 식별** — 라벨 문자열 매칭 금지, §4-1 충돌) → 그 타입 cid 들의 어댑터
    item(TModule/TPanel) 리스트 + 부재별 단면명 목록. item↔cid 는 `source_index` 로 연결.
  - 각 item → `_serialize_placement` **재사용**(단, vehicle_height_offset=0 인 가짜 Truck 또는
    offset 미적용 경로). 부재 렌더(body_parts/attached_parts/wall_segments)는 그대로.
  - 배치 좌표:
    - 같은 타입 N개 = -Y 방향 누적, 간격 = 운송 `INTRA_GROUP_GAP_M`(1.5m) 동일.
    - 다른 타입 = +X 방향 분리, 간격 = **각 타입 외곽 AABB(종속 포함) 끝과 끝 3.0m**.
  - 라벨(JSON): 타입당 1개. 텍스트 = `타입명` + 부재별 단면 목록(`기둥 SHS250×250×8` 등, 응력비 제외).
- `build_quantity_3d_html(...)` — `build_loaded_3d_three_html` 의 물량탭판. `hide_truck=true` 세팅.

HTML 템플릿 변경(운송과 공유 — 분기로 처리):
- `data.hide_truck` 플래그 → `buildTruckGroup` 의 ①~⑤(트럭/적재공간) 건너뛰고 ⑥ 화물만.
- 물량탭 라벨 텍스트는 `renderGroupLabelHtml` 대신 별도 렌더(부재 단면 목록) — `data` 에 라벨 HTML
  직접 실어 보내거나 물량탭 전용 라벨 함수 분기.

**가짜 Trip/Placement 방식 확정(§4-2, §4-보강2 강조 연동)**:
- **타입당 1 Trip** (trip_no = 타입 인덱스). 그 타입의 모든 인스턴스 = 이 Trip 의 placements N개.
- 인스턴스마다 `Placement(item, slot=floor, posture=lying, truck_xyz=(x,y,0))`. truck_xyz 로 좌표 직접.
  - 같은 타입 내 인스턴스 = y 누적(-Y, 1.5m). 다른 타입 = 다른 Trip → +X 분리(외곽끝 3m).
  - **주의**: 운송은 *같은 그룹* 회차를 y_offset 으로 겹쳤지만, 물량탭은 *한 Trip 안에서* placements
    의 truck_xyz.y 로 인스턴스를 벌린다(구조가 다름). 따라서 serialize 신규 함수에서 그룹 오프셋
    로직(`group_x_offset`/`y_off`)을 쓰지 않고, **타입(=Trip)별 x_offset + placement별 y** 로 직접 배치.
- **강조**: trip_no=타입idx 이므로 기존 `highlightTrip(trip_no)` 가 그대로 "타입 단위 강조" 가 됨.
  vehicle_height_offset=0 가짜 Truck(또는 offset 미적용)으로 바닥 배치.

  → 물량탭의 [타입]>[역할]>[부재] 트리와 **부재/타입 단위로 양방향 강조하려면**:
    (1) mesh `userData` 에 식별자(타입키 + 부재 mid 또는 cid) 를 *심는 작업* 필요(어댑터 part 에
        부재 mid 전파 → serialize → mesh).
    (2) 회차 단위 `highlightTrip` 대신 *부재/타입 단위 강조 함수* 신규.
    (3) 클릭 시 trip_no 대신 식별자를 Bridge 로 전달.
  → **강조 단위 = 타입 단위(사용자 확정 2026-05-31).** 부재 단위 강조 안 함 → **어댑터 BodyPart에
    부재 mid 를 심을 필요 없음**(운송 코드 미수정, 회귀 위험 회피). 구현:
    - **가짜 Trip 을 타입당 1개**로 만들면(한 타입의 모든 인스턴스 = 그 trip 의 placements),
      기존 `trip_no` 식별 + `highlightTrip` 회차 강조 메커니즘을 **거의 그대로 재사용** 가능.
      즉 "trip_no ≡ 타입 인덱스" 로 두면 클릭→타입 강조, 트리→타입 강조가 자연 연결.
    - 트리 노드(타입)에 그 타입 인덱스 저장 → 선택 시 Bridge 로 `highlight(타입idx)` 호출.
    - 3D 클릭 → 그 placement 의 trip_no(=타입idx) → 트리 해당 타입 행 선택.
  → 이 설계라면 §3-B 의 "가짜 Trip = 타입당 1개" 와 일관(아래 3-B 갱신). raycast/dim/호버 골격
    재사용 + 타입 단위 강조는 기존 trip 강조로 충족.

### §4-보강2. 심층 재검증 2차 발견 (데이터 생명주기 — 중대)

- ⚠ **단면설계 결과 필수 전제 문제(중대)**: 새 물량탭 3D·트리는 `derive_section_types(_section_result)`
  의 타입에 의존하는데, `_section_result` 는 **단면설계 탭을 거쳐야만** 생성된다. 사용자가 단면설계 탭을
  안 거치고 물량탭에 오면 `_section_result is None` → **타입 없음 → 3D 빈 화면**.
  추가로 배치/정의 탭 진입 시 `set_section_design_result(None)` 로 **결과가 폐기**됨(stale 방지 로직).
  - **대응(사용자 확정 2026-05-31): (B) 안내 화면 표시.**
    `_section_result is None`(또는 변환 결과 groups 비어있음)이면 3D 영역에 "단면 설계를 먼저
    실행하세요" 안내 HTML 표시(운송탭 빈 화면 패턴 재사용), 우측 트리·표는 비움.
    자동 수렴(A)은 채택 안 함 — 사용자가 단면설계 탭을 명시적으로 거치게 한다.
  - **빈/None 방어가 Phase 4 필수**. 계획 §3-D 에 반영.

- ⚠ **물량 변환 중복/불일치 위험(중대)**: 컨트롤러가 `_quantity_from_section_design()` 로 *이미*
  `converge_result_to_design_result` 를 호출해 `_design_results`(정책키) + `am` + `reports` 를
  만들어 캐시한다. 물량탭 3D 빌더가 `_section_result` 를 **다시 독립 변환**하면 이중 변환 +
  운송탭과 다른 인스턴스를 쓸 위험. **대응**: 컨트롤러의 기존 `_design_results`(또는
  `_quantity_from_section_design()` 반환) + 캐시된 `reports`/`am` 를 **재사용**한다. 새로 만들지 않는다.
  → 3-A 분해기 입력도 이 캐시된 `am` + `dr`(단일) 사용.

- ⚠ **어댑터 재호출 비용**: 운송탭은 `build_transport_input` 을 운송 계산 시 호출. 물량탭도 같은
  어댑터를 호출하면 *두 번* 변환. 다만 입력(scene,am,dr)이 같으면 결과 동일 → 물량탭 진입 시 1회
  호출해 캐시(scene 변경 전까지 유지). Phase 2에서 캐시 키(scene id + section_result id) 설계.

- **AnalysisPanel 잔여 배선 정리**: 물량탭이 `_analysis_panel` 을 더는 안 쓰면, `set_visible_subtabs
  (show_quantity=True)`, `select_envelope_case()`, `ratio_view_changed`/`member_selected` emit 등
  물량탭 전용 배선을 제거/이전해야 한다(구조해석 탭 공유분은 유지). Phase 3·4 점검 항목.

- **인스턴스 형상은 대표 1개로 복제 가능(유리)**: 어댑터 `_world_to_parent_nominal` 이 회전·앵커를
  *풀어서* nominal 좌표로 만들므로, 같은 타입의 모든 인스턴스는 body_parts 가 동일하다. → 80개를
  그릴 때 **대표 1개 형상을 좌표만 바꿔 복제**해도 정확(인스턴스마다 어댑터 재변환 불필요).
  단 사용자 요구 "80개 다 그림" 충족(개수만큼 mesh 생성). 회전 차이는 시각화에 영향 없음(정규 자세).

- **벽 흡수 패널 — 강재 귀속 누락 주의(중대)**: `merged_wall_ids` 로 패널에 흡수된 StructWall 은
  타입 목록에서 *안전하게 제외됨* — `classify_component_types` L228~230 이 `merged_fp_id` 보유
  STRUCT_WALL 을 이미 거른다(따라서 별도 타입으로 안 뜸, 이중계산 X). **그러나** 그 벽 부재(mid)는
  `comp_to_members[wall_cid]` 에 남아 *전체* 강재 합(`aggregate_steel`)에는 포함된다. wall_cid 가
  타입에 없으니 **타입별 cid 순회로는 그 강재가 누락** → "Σ타입 강재 < 전체 강재".
  → **대응**: 흡수된 벽(`merged_fp_id` 보유)의 강재를 **부모 패널(merged_fp_id 가 가리키는 cid)** 에
  귀속한다. (어댑터가 형상·자중을 부모에 흡수하는 것과 동일 귀속.) 검증식에 포함.
- **타입 시그니처 한계**: `derive_section_types` 는 *자기 컴포넌트 부재(comp_to_members)* 단면만으로
  타입을 가른다(코드 주석: 종속 부재 차이 분기는 미보강). 종속부재(캔틸 등) 단면이 달라도 같은
  타입으로 묶일 수 있음. → 물량탭 대응: **3D 라벨·단면 목록은 대표 컴포넌트값**으로 표시하되,
  **물량·금액 합산은 `comp_ids` 전체를 실제 순회해 누적**(라벨=대표, 합산=실측). 이러면 종속부재
  단면 차이가 있어도 합계는 정확. (본체 단면이 같으면 강재 대부분 동일, 종속 차이는 미미.)

### §4-보강3. 심층 재검증 5차 — 어댑터 변환 분기 (중대)

- ⚠ **타입↔3D item 불일치 방어**: 어댑터 `convert_module`/`convert_vertical3_lying`/
  `convert_floor_panel_*`/`convert_independent_wall_panel` 은 단면 룩업 실패 시 **None 반환** →
  해당 cid 가 `TransportInput` 에 없다. 타입 목록(형상 기준)엔 그 cid 가 남으므로 불일치 가능.
  - **대응**: 3D 빌더는 타입 cid → `source_index` 로 item 을 찾되, **item 이 없는 cid 는 스킵 + 진단
    로그**(어느 타입의 몇 cid 가 3D 에서 빠졌는지). 트리(물량)는 단면 룩업과 무관하게 표시되므로
    "트리엔 있는데 3D 엔 없음" 이 발생 가능 → 트리 노드에 "3D 표시 불가(단면 미배정)" 표식 검토.
  - 정상 케이스(단면 설계 수렴 완료)면 룩업 실패가 없어 불일치도 없음 — 엣지 방어 목적.

- ⚠ **VERTICAL_MODULE 세운 자세 필수 — 사용자 확정(2026-05-31)**: `convert_vertical3_lying` 이
  수직3모듈을 *운송용으로 눕혀서*(length=원래 height) 변환하나, 물량탭은 **세운 자세로 표시해야 함**.
  - **대응 — ✅ Phase 2 확인: 옵션 하나로 해결**. 별도 경로 불필요. `convert_vertical3_lying` 은
    `treat_v3_module_as_lying=False` 면 *눕힘 재매핑(`_remap_part_v3_lying`)을 건너뛰고* 세운
    nominal 형상(`_collect_v3_body_parts` 원본, height=h)을 그대로 반환한다(adapter L999~1010).
    → 물량탭은 어댑터를 `TransportOptions(treat_v3_module_as_lying=False)` 로 호출하면 끝(Phase 4).
  - ✅ **좌표 매핑 분석 — 일반 모듈은 세워 보임(확정)**: three.js `pyToThree(x,y,z)={x, y:z, z:y}` —
    Python z(높이)→three Y(위)로 **높이축 보존**. 어댑터 X-Y 교환(L371~376)은 length↔width 로 둘 다
    *수평축* → 평면상 90° 회전일 뿐 세움/눕힘과 무관. ∴ **일반 단층 모듈·패널은 운송 3D 에서도
    정상적으로 세워(바닥에 놓여) 보인다.** 물량탭도 동일 → 일반 모듈 자세 문제 없음.
  - **v3 만 눕힘 회전**(`convert_vertical3_lying` 가 height→length 로 실제 자세를 바꿈) → v3 만 세운
    경로 신설 대상. (평면 90° 회전은 물량 확인 목적상 무해 — 사용자가 정방향 정렬을 추가 요구하면
    그때 보정.)
